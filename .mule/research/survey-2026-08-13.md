## Source 3 — upstream `astarte-platform` (`684da75`, moved 08-10/08-12)

`git log f65bda5d..684da75` is 6 commits. Grouped by relevance:

### Infra — `astarte_vmq_plugin` monorepo import (all 6 commits)

`261fbcd` imports the plugin into the monorepo under `apps/astarte_vmq_plugin`
(previously the standalone `astarte-platform/astarte_vmq_plugin` repository);
`68c9b9a`/`dd7860e`/`684da75` wire its CI and config, `99733a3`/`12d59ca` fix
compile/lint errors the import surfaced. `docker-compose.yml` now builds the
VerneMQ image from the plugin, and `committed.toml` adds the `vmq_plugin`
commit scope. No CHANGELOG entry, no new tag (newest remains `v1.4.0-rc.4`,
08-06), no `doc/` changes — so the keyAgreement doc-lag noted on 08-08
(`080-mqtt-v1-protocol.md:174-176`) still stands.

This is the broker-side glue Astrate replaces with its own embedded broker
(`internal/broker/`), so the import changes nothing wire-visible. Because the
plugin is now greppable in one place, I read it and checked its wire-visible
behaviours against Astrate's broker — three observations, all **no gap**:

1. **Connect-time device auth** (`lib/astarte_vmq_plugin.ex:301-315`): rejects
   a device CONNECT with `:device_does_not_exist` or `:device_deletion_in_progress`.
   Astrate's `authhook.go` `OnConnectAuthenticate` rejects with
   `deny("device lookup failed")` when `GetDevice` fails and
   `deny("device is inhibited")` for inhibition — the same outcome. Notably,
   upstream's DB-unreachable posture is *not* fail-open despite the `device_exists?`
   fallback returning `true` (`queries.ex` `Xandra.ConnectionError` → `true`,
   `astarte_vmq_plugin.ex:336-344`): the next check,
   `device_deletion_in_progress?`, conservatively returns `true` on the same
   error (`astarte_vmq_plugin.ex:346-364`) and rejects the connection with
   `:device_deletion_in_progress`. Both sides fail closed on store outage; only
   the CONNACK reason string differs (cosmetic). No gap.
2. **Publish-size cap** (`registration_modifiers`, `astarte_vmq_plugin.ex:317-326`):
   `max_message_size: 65_535` (payload cap) plus `max_inflight_messages: 100`.
   Astrate caps inbound packets at `DefaultMaxPacketBytes = 128 * 1024`
   (`broker.go:33-35`) and payloads at `DefaultMaxSize = 64 << 10` =
   65,536 bytes (`pkg/payload/value.go:94`; `max_payload_bytes` config
   default, `config.example.toml:51`). Off-by-one at the exact boundary
   (a 65,536-byte payload is accepted by Astrate, rejected by upstream) — of no
   practical consequence, no SDK emits a boundary-exact payload; noted, not a
   candidate.
3. **Connection synchronizer + device heartbeat** (`connection/synchronizer.ex`,
   `on_register`/`handle_heartbeat`, `device_heartbeat_interval_ms` in
   `astarte_vmq_plugin.schema:77`): upstream tracks cross-node device connection
   state and publishes an internal `/heartbeat`. Astrate is the broker itself
   (single process, `docs/DESIGN.md` §6) and records connect/disconnect
   natively (`SetDeviceConnected`/`SetDeviceDisconnected`, `authhook.go:32-34`).
   Structural non-gap.

The ACL rule in the plugin (`String.split(client_id, "/") == Enum.take(topic_tokens, 2)`,
`astarte_vmq_plugin.ex:66`) matches Astrate's base-topic ACL (`aclhook.go`) — a
confirmation, not a gap.
