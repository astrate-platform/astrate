## Source 1 — Astrate codebase and docs

### TODO markers

Exactly one sanctioned `// TODO` remains, per `docs/ROADMAP.md` §0.1 rule 3 (three were
sanctioned; `lttb` closed in M12-07, trigger forwarding closed in M12-08):

- `internal/store/store.go:135` — external-bus intake (`docs/DESIGN.md` §1.4). Blocked on
  GitHub issue #10 (design decision needed).

### Trigger scope: accepted-but-never-firing conditions

`internal/engine/triggers/match.go:9-13` documents the boundary explicitly: these trigger types
compile successfully (install round-trips) but **never match and never fire**:

- `value_change` (line 30)
- `value_change_applied` (line 33)
- `path_created` (line 36)
- `path_removed` (line 39)
- `value_stored` (line 42)
- `device_empty_cache_received` (line 49)
- `interface_minor_updated` (line 61)

This is a deliberate v1 scope boundary, not a defect.

### Trigger types completely absent from Astrate

Upstream Astarte (doc `060-triggers.md`) defines these device trigger types that Astrate has no
constant for and never handles:

- `device_registered` — fires when a device is registered via Pairing API
- `device_deletion_started` — fires when device deletion begins
- `device_deletion_finished` — fires when device deletion completes

Astrate performs synchronous device deletion (`COMPATIBILITY.md` deviation 9), so
`device_deletion_started`/`device_deletion_finished` are a structural mismatch, not just a gap.
`device_registered` is a gap — Astrate's pairing service (`internal/pairing/service.go`) never
emits a trigger event on registration.

### Group-scoped triggers not implemented

`internal/engine/triggers/match.go:11-12` notes group-scoped triggers compile but never match.
Upstream `060-triggers.md` documents `group_name` as a parameter on both device and data triggers.
The unmeasured group WATCH shapes in `COMPATIBILITY.md` deviation 1 are related — they depend on
groups existing, which the bench realm does not have.

### Protocol topics not implemented

**Capabilities** (`/<realm>/<device_id>/capabilities`): upstream MQTT v1 protocol doc
(`080-mqtt-v1-protocol.md` lines 17-18, 119-136) defines a BSON payload on this topic that sets
device capabilities (currently only `purge_properties_compression_format`: `"zlib"` or
`"plaintext"`). Astrate's broker ACL (`internal/broker/aclhook.go`) does not publish-allow this
topic; the engine does not parse it. Upstream's `data_handler.ex` processes capabilities messages
and stores them per-device. The CHANGELOG v1.3.1 notes a "capabilities message stalling queues"
bugfix, indicating this is a live, exercised feature in upstream.

**Key Agreement** (`/<realm>/<device_id>/control/keyAgreement`): upstream MQTT v1 protocol doc
(`080-mqtt-v1-protocol.md` lines 22-23, 172-176) defines a CBOR-payload topic for a
cryptographic key agreement handshake (sub-paths `/0` through `/4` for InitExchange,
ExchangeResp, SecretHash, HashOk, ExchangeFailed — `control_handler.ex` lines 49-53). The
protocol doc notes it is "reserved and routed correctly, but the handshake protocol is not yet
implemented" in upstream either. Astrate does not handle this topic at all.

### Trigger action limitations

**Mustache templates**: upstream `060-triggers.md` lines 516-543 documents a
`template_type: "mustache"` action that renders HTTP request bodies from Mustache templates with
access to `{{ realm }}`, `{{ device_id }}`, `{{ trigger_name }}`, `{{ event_type }}`, and all
event fields. Astrate's trigger actions (`internal/engine/triggers/actions.go`) only implement
the default JSON action (lines 496-497 and the test at line 497).

**`ignore_ssl_errors`**: upstream `060-triggers.md` line 234 documents this optional boolean on
HTTP actions. Astrate's trigger action config does not include it (the `httptest` server in tests
uses plain HTTP, never exercises TLS error handling).

### `device_error.error_name` — two unverified rows

`docs/COMPATIBILITY.md` deviation 1 (lines 121-124) states explicitly:

- `write_on_server_owned_interface` — unverified because the bench realm has no server-owned
  interface. Upstream's `data_handler.ex` line 543-545 emits this error_name when a device
  publishes on a server-owned interface.
- `value_size_exceeded` — unverified because upstream accepted a 100 KB string in the test.
  Upstream's `data_handler.ex` line 585-591 emits this error_name when value validation returns
  `:value_size_exceeded`. The upstream size limit is not documented; it may be a Cassandra write
  limit rather than an application-level check.

### Upstream error names outside the Dashboard's validated set

`internal/engine/triggers/errorname.go` carries the Dashboard v1.2.2 validated set (15 names).
Upstream `data_handler.ex` and `control_handler.ex` emit additional error names not in that set,
meaning they would be discarded by the Dashboard even when emitted by upstream Astarte itself:

- `missing_required_mapping` (`data_handler.ex:358`)
- `unset_on_datastream` (`data_handler.ex:375`)
- `purge_properties_error` (`control_handler.ex:144`)
- `key_agreement_transition_error` (`control_handler.ex:210,229,357`)
- `key_agreement_error` (`control_handler.ex:256`)
- `secret_hash_error` (`control_handler.ex:299`)
- `hash_ok_error` (`control_handler.ex:382`)
- `exchange_failed_error` (`control_handler.ex:639`)
- `device_session_not_found` (`control_handler.ex:997`) — this one IS in the set
- `resend_interface_properties_failed` (`control_handler.ex:1012`) — also in the set
- `empty_cache_error` (`control_handler.ex:1030`) — also in the set
- `unexpected_internal_message` (`data_handler.ex:56` — internal handler)

The non-Dashboard names are a mix of internal operational errors and key-agreement errors. Whether
they ever surface to Channels consumers is unclear from source alone; they are all constructed as
`DeviceErrorEvent` structs with an `error_name` field.

### Code-vs-docs disagreement

None found. The frozen docs (`DESIGN.md`, `ROADMAP.md`) and the code are consistent. The one
apparent discrepancy — `docs/ROADMAP.md` §0.1 rule 3 listing three sanctioned TODOs, only one
of which remains — is explained by M12 phases 07 and 08 having closed the other two, with the
rule deliberately not edited (per `COMPATIBILITY.md` and `.trickle/plan.md`).

## Source 3 — upstream `astarte-platform` (v1.4.0-rc.2, shallow clone)

### CHANGELOG highlights since v1.2.0 (the version Astrate benchmarks against)

From `CHANGELOG.md`:

- **v1.3.0**: AMQP triggers vhost now realm-scoped (`/[astarte_instance_id]_[realm_name]`);
  realm replication strategy defaults to `NetworkTopologyStrategy` from ScyllaDB topology.
- **v1.3.1**: Capabilities message stalling queues bugfix; immediately delete devices in best
  case scenario.
- **v1.3.2**: Avoid crash on invalid properties message.
- **v1.4.0-rc.0**: FIDO Device Onboard v1.1 for device registration (experimental, disabled by
  default); `required` flag for object-aggregated mappings; `detailed=true` on interface listing.
- **v1.4.0-rc.1/2**: `HOUSEKEEPING_DEFAULT_DATASTREAM_MAXIMUM_STORAGE_RETENTION` for instance-wide
  default retention; FDO enabled by default; fixed rotated FDO keys.

### Interface schema

`doc/pages/architecture/040-interface_schema.md`: 14 value types (7 scalars + 7 arrays) — same
set Astrate implements. Mapping fields are identical to what `docs/DESIGN.md` §2.2 specifies.
The upstream schema allows additional properties (line 30/150), which means interface definitions
with unknown extra fields are accepted; Astrate should do the same (and does, via
`pkg/interfaceschema` which ignores unknown fields).

### MQTT v1 protocol

`doc/pages/architecture/080-mqtt-v1-protocol.md`: confirms everything in `docs/DESIGN.md` §3.1-3.4.
Notable details:

- **Capabilities topic** (lines 17-18, 119-136): BSON payload, sets
  `purge_properties_compression_format`. Default is `"zlib"`. If a capabilities message is
  malformed, the device gets forcefully disconnected and previously stored values remain unchanged.
  This is a live feature — the CHANGELOG v1.3.1 bugfixes prove it is exercised in production.
- **Key Agreement topic** (lines 22-23, 172-176): CBOR payload, sub-paths `/keyAgreement/0`
  through `/4`. Documented as "reserved and routed correctly, but the handshake protocol is not
  yet implemented" — so both upstream and Astrate are aligned in not supporting it.
- **Minimal Protocol section** (lines 287-290): documents that devices may omit
  `consumer/properties`, `producer/properties`, and `emptyCache` if they have no property
  interfaces. This is relevant for minimal AtomVM devices.

### Triggers

`doc/pages/architecture/060-triggers.md`: full trigger documentation. Key points for parity:

- 6 data trigger types: `incoming_data`, `value_stored`, `value_change`, `value_change_applied`,
  `path_created`, `path_removed` — Astrate implements only `incoming_data`.
- 10 device trigger types: `device_connected`, `device_disconnected`, `device_error`,
  `device_registered`, `device_deletion_started`, `device_deletion_finished`,
  `incoming_introspection`, `interface_added`, `interface_removed`, `interface_minor_updated` —
  Astrate implements 6 of these (all except `device_registered`, `device_deletion_started`,
  `device_deletion_finished`, and `interface_minor_updated` which is accepted but not evaluated).
- `group_name` on both device and data triggers — not implemented in Astrate.
- Mustache template actions — not implemented in Astrate.
- `ignore_ssl_errors` on HTTP actions — not implemented in Astrate.
- `Astarte-Realm` header sent with HTTP actions (line 265) — Astrate sends this
  (`internal/engine/triggers/actions.go:497`).

### Trigger Delivery Policies

`doc/pages/architecture/062-trigger_delivery_policies.md`: documents `prefetch_count` (optional,
defaults to 1). Astrate implements the policy schema but not `prefetch_count`
(`COMPATIBILITY.md` deviation 8). The upstream doc notes that `prefetch_count > 1` increases
throughput but loses event ordering — this is a deliberate tradeoff.

### Pairing

`doc/pages/architecture/050-pairing_mechanism.md`: upstream pairing flow matches `docs/DESIGN.md`
§4.4 exactly. Upstream `POST /agent/devices` accepts `hw_id` (same format). No divergence found.

### Standard interfaces

`standard-interfaces/` contains 6 JSON files (genericsensors.Values, genericsensors.AvailableSensors,
genericsensors.SamplingRate, genericsensors.Geolocation, genericcommands.ServerCommands,
genericevents.DeviceEvents). These are the reference interfaces Astrate should be able to install
and validate against.

### Trigger error names outside Dashboard's validated set

Upstream emits error names (`missing_required_mapping`, `unset_on_datastream`,
`purge_properties_error`, key-agreement error names, `unexpected_internal_message`) that are not
in the Dashboard v1.2.2 `nke` validation array. These are either internal errors unlikely to
reach a Channels consumer or key-agreement errors for an unimplemented feature. The risk is low
but worth noting: if the Dashboard is upgraded, new error names may need to be added to
`upstreamErrorNames` in `errorname.go`.

## Source 5 — upstream `atomvm/AtomVM`

### The connection to Astrate

AtomVM is a minimal Erlang/Elixir VM for microcontrollers (ESP32, STM32, Raspberry Pi Pico).
Astrate's `docs/DESIGN.md` §3.5 explicitly names AtomVM as the motivation for the dual-payload
(JSON + BSON) codec: a full BSON encoder is "dead weight" on ultra-constrained targets, while
JSON is a small pure-Erlang library.

**AtomVM contains zero references to "astarte"** (confirmed: `grep -ri astarte` over the
AtomVM repo returns nothing). The `atomvm` GitHub org also has no Astarte-protocol client
library.

The plausible connection is one-directional: AtomVM provides a *platform* on which someone could
build an Astarte-protocol device client in Erlang/Elixir. Astrate's JSON payload profile
(`docs/DESIGN.md` §3.5.3) exists precisely for that use case. But no such client exists today in
the AtomVM ecosystem.

**Conclusion:** AtomVM is relevant to Astrate only as a target platform for the JSON payload
profile. It does not ship an Astarte client, and no evidence suggests one is in development.
Astrate's JSON profile spec (`docs/JSON-PAYLOAD-PROFILE.md`) is the correct document to maintain
for potential AtomVM device authors. There is no AtomVM-specific work item for Astrate itself.
