### key-agreement-protocol
Title: Handle the `<realm>/<device_id>/control/keyAgreement` CBOR topic
Scope: mule-spec
Body:
Carried forward unchanged from `issues-2026-08-01.md` (re-grep-confirmed: only the
ACL deny comment `internal/broker/aclhook.go:65` and its test
`aclhook_test.go:53`). Upstream has implemented the full ECDH key agreement
protocol since v1.4.0-rc.2: a 5-message CBOR handshake over `keyAgreement/0`
through `/4` (`InitExchange`, `ExchangeResp`, `SecretHash`, `HashOk`,
`ExchangeFailed`), X25519 (suite 1, default) and ECDH P-256 (suite 0), a 32-byte
AES-256-GCM key derived via HKDF and persisted in `devices.shared_secret`, since
`5047681` encrypted at rest with the realm KEK. The fix and verification remain
exactly as written on 08-01: (a) allow the topic in the broker ACL for the
device's own base, (b) decode the 5 CBOR message types, (c) implement the state
machine, (d) derive and persist the shared secret, (e) emit the upstream error
names on failure; verify with a T3 handshake test and an invalid-InitExchange test
asserting `key_agreement_error`. Prerequisite for `encrypted-endpoints` below.

### encrypted-endpoints
Title: Implement encrypted endpoints (DEK/KEK at-rest encryption, COSE transport encryption, parameter-aware)
Scope: mule-spec
Body:
Carried forward from `issues-2026-08-01.md`, **updated for upstream `85c05c67`**
(`b61a3ed33`, #2112). Upstream has two encryption layers for mappings with
`encrypted: true`: (1) at-rest DEK/KEK wrapping via Astarte Secrets, stored in the
`encryptedblob_value`/`encrypted_dek` columns, with the per-device shared secret
encrypted under the realm KEK since `5047681`; (2) COSE Encrypt0 transport using
the key-agreement shared secret. Since #2112 the upstream data handler also: (a)
filters the encrypted-endpoint set to the **current interface**
(`&1.interface_id == context.interface_id` in `data_handler.ex` — previously it
took every encrypted mapping in the device's introspection), and (b) uses the
**mapping's endpoint** as the encryption context path, which is what allows an
encrypted mapping on a parametrized endpoint like `/%{some_param}/encryptedValue`.
Astrate has zero DEK/KEK/COSE references (`git grep -i "dek\|kek\|cose"
origin/main -- internal/` matches only `fakeKeys`/`KeySource` test doubles — the
feature is absent). The fix: (a) encrypted-value columns on properties/datastream
tables, (b) a secrets library for DEK generation/wrapping and shared-secret
encryption, (c) encrypt on write when the mapping is `encrypted: true`, with the
interface-scoped and parameter-aware endpoint resolution matching #2112 (the
mapping endpoint, with `%{param}` substituted, not the raw inbound path), (d)
decrypt on read, (e) COSE Encrypt0 for server-to-device transport. Verification: a
T3 test with an encrypted endpoint — including one on a parametrized path, per
the upstream fixture shape — asserting values store encrypted and decrypt on read,
and that writing without a shared secret emits
`device_not_ready_for_encryption`. Follows `key-agreement-protocol`.

### capabilities-malformed-disconnect
Title: Match upstream's malformed-capabilities handling (force-disconnect + `malformed_capabilities_message` error_name)
Scope: mule-line
Body:
Carried forward from `issues-2026-08-01.md` (re-grep-confirmed against
`origin/main`: `handleCapabilities` in `internal/engine/capabilities.go` still
calls `e.reject` on decode/validate failure and keeps the connection, and
`malformed_capabilities_message` is still absent from `errorname.go`). Upstream
forcefully disconnects the device on a malformed capabilities message
(`080-mqtt-v1-protocol.md:125-128`), leaving stored values unchanged, and fires a
device_error with `error_name: "malformed_capabilities_message"`
(`capabilities_handler.ex:74-81`, `error.ex:79-87`,

engine's `BrokerPort`, call it on the malformed path, map
`capabilities_payload_invalid` → `malformed_capabilities_message` in
`errorname.go`; T2 test asserting session termination + the correct error_name.
Secondary note (also unchanged): upstream persists capabilities per device
(`090-database.md:123-129`), Astrate keeps them in-memory and session-scoped —
record as a documented divergence in `docs/COMPATIBILITY.md` if not persisted.

### unset-not-allowed-mapping
Title: Fix `unset_not_allowed` error name mapping to match upstream
Scope: mule-line
Body:
Carried forward from `issues-2026-08-01.md` (re-grep-confirmed: `errorname.go:62`
still maps `"unset_not_allowed"` → `"unexpected_value_type"`). When a device tries
to unset a property with `allow_unset: false`, Astrate's decoder
(`pkg/payload/payload.go:68-69`) returns `ReasonUnsetNotAllowed`; the engine
rejects with reason `"unset_not_allowed"` and `errorname.go` maps it to
`"unexpected_value_type"`. Upstream emits the literal error name `"unset_not_allowed"`
(`data_handler.ex:255-260`), so the Dashboard/channels consumer sees a different
name than upstream would send for the same rejection. The fix: change the mapping
in `errorname.go` from `"unset_not_allowed": "unexpected_value_type"` to a
pass-through. `unset_not_allowed` is not in the Dashboard v1.2.2 validated set,
so the Dashboard discards the event either way — but the emitted name then matches
upstream's, which is the parity contract. Verification: a T1 test asserting
`UpstreamErrorName("unset_not_allowed")` returns `"unset_not_allowed"`; update the
existing test at `errorname_test.go` that expects the corrected value.
