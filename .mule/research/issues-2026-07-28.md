### key-agreement-protocol
Title: Handle the `<realm>/<device_id>/control/keyAgreement` CBOR topic
Scope: mule-spec
Body:
Upstream Astarte has implemented the full ECDH key agreement protocol since v1.4.0-rc.2
(30+ commits, primarily `apps/astarte_data_updater_plant/`). The protocol uses a 5-message
handshake over CBOR-encoded MQTT control topics (`keyAgreement/0` through `/4`): `InitExchange`,
`ExchangeResp`, `SecretHash`, `HashOk`, `ExchangeFailed`. It supports X25519 (suite 1, default)
and ECDH P-256 (suite 0), derives a 32-byte AES-256-GCM symmetric key via HKDF, and persists
it in the `devices.shared_secret` column as a COSE symmetric key struct. Astrate's broker
(`internal/broker/aclhook.go`) does not publish-allow this topic, and the engine has no handler
for it — `grep -rn "key_agreement\|keyAgreement\|KeyAgreement" internal/` returns nothing. The
fix: (a) allow the key agreement topic in the broker ACL for the device's own base, (b) add a
CBOR decoder for the 5 message types, (c) implement the state machine (`uninitialized` →
`handshake_started` → `established` or `failed`), (d) derive the shared secret and persist it,
(e) emit the appropriate error names on failure. Verification: a T3 test with a test device
performing the full handshake; assert the derived key matches; publish an invalid `InitExchange`
and assert `key_agreement_error` is emitted.

### encrypted-endpoints
Title: Implement encrypted endpoints (DEK/KEK at-rest encryption and COSE transport encryption)
Scope: mule-spec
Body:
Upstream now has two encryption layers for interface mappings with `encrypted: true`. (1)
**At-rest**: per-write Data Encryption Keys (DEKs) generated via OpenBao Transit Engine,
wrapped under a realm-level Key Encryption Key (KEK), stored in new `encryptedblob_value` and
`encrypted_dek` DB columns (migrations `0022`, `0023`). (2) **Transport**: server-to-device
payloads are wrapped in COSE Encrypt0 messages using the per-device shared symmetric key from
the key agreement handshake. Astrate has zero references to DEK, KEK, COSE, or encrypted
endpoints (`grep -ri "dek\|kek\|coise\|encrypted_endpoint" internal/` returns nothing). This is
a major subsystem requiring DB schema changes, OpenBao integration (or a local equivalent),
COSE library dependency, and changes to both the write path (DUP) and read path (AppEngine).
The fix: (a) add `encryptedblob_value` and `encrypted_dek` columns to properties and datastream
tables, (b) integrate a secrets library for DEK generation/wrapping, (c) encrypt values on write
when the mapping has `encrypted: true`, (d) decrypt on read, (e) implement COSE Encrypt0 for
server-to-device transport. Verification: a T3 test with an encrypted endpoint; write a value,
assert it is stored encrypted in the DB; read it back, assert decryption succeeds; write without
a shared secret and assert `device_not_ready_for_encryption` is emitted.

### unset-not-allowed-mapping
Title: Fix `unset_not_allowed` error name mapping to match upstream
Scope: mule-line
Body:
When a device tries to unset a property with `allow_unset: false`, Astrate's decoder
(`pkg/payload/payload.go:68-69`) returns `ReasonUnsetNotAllowed`. The engine rejects the message
with reason `"unset_not_allowed"` (`internal/engine/data.go:275`), and the error name mapping
(`internal/engine/triggers/errorname.go:62`) converts this to `"unexpected_value_type"`. But
upstream's actual error name for this condition is `"unset_not_allowed"` (`data_handler.ex:161`).
The Dashboard receives `"unexpected_value_type"` when it should receive `"unset_not_allowed"`.
The fix: change the mapping in `errorname.go` from `"unset_not_allowed": "unexpected_value_type"`
to `"unset_not_allowed": "unset_not_allowed"` (pass-through). Verification: a T1 test that
asserts `UpstreamErrorName("unset_not_allowed")` returns `"unset_not_allowed"`; the existing
test at `errorname_test.go:30` must be updated to expect the corrected value.

### device-registered-trigger
Title: Emit a `device_registered` trigger event on pairing registration
Scope: mule-line
Body:
Upstream Astarte fires a `device_registered` device trigger when a device is registered via the
Pairing API (`060-triggers.md:109`). Astrate's pairing service (`internal/pairing/service.go`)
never emits a trigger event on registration — confirmed by `grep -rn "device_registered"
internal/` returning nothing. This means any upstream trigger with `on: device_registered` installs
successfully but never fires. The fix: after successful registration in the pairing service, emit a
`DeviceRegisteredEvent` on the trigger bus (the same path `device_connected` uses). Verification:
add a test in `internal/pairing/service_test.go` that registers a device and asserts the trigger
bus receives a `DeviceRegisteredEvent` with the correct device ID and realm; the test must fail
without the change.

### group-watch-paths
Title: Measure and reconcile group WATCH authorization paths against upstream
Scope: mule-spec
Body:
`docs/COMPATIBILITY.md` deviation 1 (line 96) marks the group WATCH shapes
(`groups/<name>/<interface><match_path>` and `groups/<name>`) as "not measured, the realm having
no group." The bench upstream on the Legion has no group provisioned. This needs: (a) provision a
group in the bench realm with at least one device, (b) mint a narrow-`a_ch` token authorising a
WATCH on the group shape, (c) record the upstream's accept/reject against the recorded fixture
format (`test/conformance/upstream/channels.json`), (d) reconcile Astrate's
`Token.AuthorizesChannel` implementation. The group shapes rest on the same upstream function whose
device shapes M12 phase 06b confirmed, but they have never been observed. Verification: a
recording run against the self-hosted upstream that produces fixture rows for the group WATCH
shapes; the fixture is committed to `test/conformance/upstream/` and a test asserts Astrate's
behaviour matches.

### prefetch-count-delivery-policies
Title: Implement `prefetch_count` on trigger delivery policies
Scope: mule-line
Body:
Upstream's trigger delivery policies (`062-trigger_delivery_policies.md:52`) support an optional
`prefetch_count` field that controls how many unacknowledged event messages a consumer can hold.
Astrate's policy implementation (`internal/engine/triggers/policy.go`) does not include this
field. The upstream default is 1 (ordered processing); values > 1 increase throughput but lose
ordering. Verification: add `PrefetchCount int` to the policy config struct, enforce the default
of 1, add a T1 test that round-trips a policy JSON with `prefetch_count` set; confirm the value
is stored and retrievable. A higher-level test asserting ordering vs. throughput tradeoff is out
of scope for a mule-line.
