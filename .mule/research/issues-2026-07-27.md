### device-registered-trigger
Title: Emit a `device_registered` trigger event on pairing registration
Scope: mule-line
Body:
Upstream Astarte fires a `device_registered` device trigger when a device is registered via the
Pairing API (`060-triggers.md:109`). Astrate's pairing service (`internal/pairing/service.go`)
never emits a trigger event on registration — confirmed by `grep -rn "device_registered"
internal/` returning nothing. This means any upstream trigger with `on: device_registered` installs
successfully but never fires. The fix: after successful registration in the pairing service, emit a
`DeviceRegisteredEvent` on the trigger bus (the same path `device_connected` uses). Verification:
add a test in `internal/pairing/service_test.go` that registers a device and asserts the trigger
bus receives a `DeviceRegisteredEvent` with the correct device ID and realm; the test must fail
without the change.

behaviour matches.

### capabilities-topic
Title: Handle the `<realm>/<device_id>/capabilities` BSON topic
Scope: mule-spec
Body:
Upstream's MQTT v1 protocol (`080-mqtt-v1-protocol.md:119-136`) defines a `<realm>/<device_id>/capabilities`
topic with a BSON payload that sets device capabilities. Currently the only capability is
`purge_properties_compression_format` (values `"zlib"` or `"plaintext"`, default `"zlib"`).
Astrate's broker ACL (`internal/broker/aclhook.go`) does not allow publishing to this topic, and
the engine does not parse it. Upstream's `data_handler.ex` processes capabilities and stores them
per-device; v1.3.1 fixed a "capabilities message stalling queues" bug, proving this is exercised
in production. The fix: (a) allow the capabilities topic in the broker ACL for the device's own
base, (b) add a capabilities handler in the engine that decodes the BSON payload, validates known
capability names, and stores the value, (c) disconnect the device on malformed messages (upstream
behaviour). Verification: a T3 test with a test device publishing a valid capabilities BSON
document; assert the capability is stored and retrievable; publish a malformed capabilities
document and assert the device is disconnected.

### device-deletion-triggers
Title: Emit `device_deletion_started` and `device_deletion_finished` trigger events
Scope: design-decision
Body:
Upstream Astarte fires `device_deletion_started` when device deletion begins and
`device_deletion_finished` when it completes (`060-triggers.md:109-110`). Astrate performs
synchronous device deletion (`COMPATIBILITY.md` deviation 9) and emits neither event. Because
Astrate's deletion is synchronous and atomic (one transaction), there is no "in progress" state
to expose. The design decision: should Astrate emit both events in rapid succession (started then
finished, for trigger compatibility), emit only `device_deletion_finished` (the end state is the
only observable one), or skip both (documenting the divergence as deliberate)? A device registered
trigger that fires `device_deletion_started` followed immediately by `device_deletion_finished`
would satisfy downstream consumers that check for the deletion lifecycle, but it adds complexity
for questionable value. This needs a human call before anything is coded.

### mustache-trigger-actions
Title: Implement Mustache template rendering for HTTP trigger actions
Scope: design-decision
Body:
Upstream Astarte (`060-triggers.md:516-543`) supports `template_type: "mustache"` on HTTP trigger
actions, rendering the request body from a Mustache template with access to `{{ realm }}`,
`{{ device_id }}`, `{{ trigger_name }}`, `{{ event_type }}`, and all event fields. Astrate
currently accepts this configuration (`internal/engine/triggers/actions.go:46`) but sends the
default JSON envelope regardless (`actions.go:69`, noted as unsupported). The decision: implement
Mustache rendering (adds a Go Mustache library dependency, which ROADMAP §0.1 freezes as pinned —
this would need to be added), or document the divergence and keep the default envelope. If
implemented, verification would be a T1 test rendering a template with known event fields and
comparing the output byte-for-byte against an upstream-recorded fixture.

### value-size-exceeded-verification
Title: Verify `value_size_exceeded` error_name and upstream's size limit
Scope: mule-spec
Body:
`docs/COMPATIBILITY.md` deviation 1 (lines 123-124) marks `value_size_exceeded` as an unverified
guess because upstream accepted a 100 KB string without bracketing a size limit. Upstream's
`data_handler.ex:585-591` emits this error_name when value validation returns
`:value_size_exceeded`. The limit may be a Cassandra write constraint rather than an
application-level check, making it deployment-dependent. The fix: bisect payload sizes against the
self-hosted upstream to find the threshold (if any), record the error_name at the threshold, and
document the finding. Verification: a recording that captures the error_name at the boundary and
a test that asserts Astrate's `MaxPayloadBytes` config aligns with (or deliberately differs from)
the upstream limit.

### keyagreement-topic
Title: Document the `keyAgreement` topic as a deliberate non-implementation
Scope: mule-line
Body:
Upstream's MQTT v1 protocol doc (`080-mqtt-v1-protocol.md:172-176`) defines the
`/<realm>/<device_id>/control/keyAgreement` topic for a CBOR-payload cryptographic key agreement
handshake. The doc itself says "the handshake protocol is not yet implemented" in upstream, so
both upstream and Astrate are aligned in not supporting it. However, Astrate's broker
(`internal/broker/aclhook.go`) does not allow publishing to this topic at all — a device that
attempts key agreement gets a broker-level denial rather than a graceful "not supported" response.
Verification: add a comment in the broker ACL or a doc section noting the topic is deliberately
not supported, matching upstream's own "reserved and routed" status; add a T1 test that asserts
the topic is denied with a logged reason, ensuring a future implementation gets a clear code
path.

### value-change-trigger-types
Title: Decide whether to evaluate `value_change`/`path_*` trigger types in v1
Scope: design-decision
Body:
`internal/engine/triggers/match.go:30-42` defines five data trigger types (`value_change`,
`value_change_applied`, `path_created`, `path_removed`, `value_stored`) that compile successfully
but never match — they are documented as "accepted, not evaluated in v1". Upstream evaluates all
of them (`060-triggers.md:159-170`). These trigger types require comparing against the previous
value (for `value_change`) or detecting path creation/deletion (for `path_created`/`path_removed`),
which means the engine needs to read the previous state from the database before evaluating the
condition. The decision: implement these in v1 (adds a DB read per matching message), defer to a
later milestone, or document the divergence? This needs a human call on scope vs. complexity.

### group-scoped-triggers
Title: Decide whether to support group-scoped triggers in v1
Scope: design-decision
Body:
`internal/engine/triggers/match.go:11-12` notes group-scoped triggers compile but never match.
Upstream supports `group_name` on both device and data triggers (`060-triggers.md:121-123`),
restricting the trigger to members of a named group. Supporting this requires the engine to check
the device's group membership at trigger evaluation time, which means a DB lookup or a cached
group-membership map. The decision: implement group-scoped triggers in v1 (adds complexity to the
trigger matcher and a dependency on the groups table), or document the divergence? This is
related to the group WATCH paths issue — both need groups to exist in the bench realm for
verification.

### prefetch-count-delivery-policies
Title: Implement `prefetch_count` on trigger delivery policies
Scope: mule-line
Body:
Upstream's trigger delivery policies (`062-trigger_delivery_policies.md:52`) support an optional
`prefetch_count` field that controls how many unacknowledged event messages a consumer can hold.
Astrate's policy implementation (`internal/engine/triggers/policy.go`) does not include this
field. The upstream default is 1 (ordered processing); values > 1 increase throughput but lose
ordering. Verification: add `PrefetchCount int` to the policy config struct, enforce the default
of 1, add a T1 test that round-trips a policy JSON with `prefetch_count` set; confirm the value
is stored and retrievable. A higher-level test asserting ordering vs. throughput tradeoff is out
of scope for a mule-line.
