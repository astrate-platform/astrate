### What `662d4f1` does, and why it matters

It moves volatile-trigger handling out of the appengine→data-updater relay and into `astarte_rpc`
(`libs/astarte_rpc/lib/astarte_rpc/volatile_triggers/{volatile_triggers,volatile_trigger_installation,volatile_trigger_deletion,client}.ex`,
all new). The commit message names three effects:

1. avoids the double relay appengine → dup RPC → device process;
2. **allows installation of volatile (transient) triggers for not-yet-registered devices** — this
   is the user-visible change;
3. cleans up the code.

Known upstream limitations carried in the same commit message: volatile triggers still install only
on DUP (no targeted/individual-device volatile installation yet), and a restarting/ascent of a new
replica forgets previously-installed volatile triggers (they are, by design, volatile).

This is an internal Astarte architecture change — there is **no wire-protocol change** for the
Channels `watch` payload and no doc change. The wire-visible delta is purely: upstream now *accepts*
a transient trigger for a device that is not yet registered.

### Parity consequence for Astrate

Astrate's Channels `watch` path (`internal/appengine/channels/ws.go:280-317` → `room.go:115-137`)
never checks whether the target device is registered; `Watch` compiles the condition, stores it by
name, and returns `nil`. So Astrate **already** allows installing a transient trigger for a
not-yet-registered device — the exact capability upstream just unblocked with `662d4f1`.

**This is a parity confirmation, not a gap.** Astrate is a superset here: the behaviour upstream
went to some effort to enable has been available in Astrate all along, with no code change.

No candidate is opened by this change. It is recorded so a future diff can be understood:
if Astrate later adds a registration check to its `watch` path (e.g. to match some upstream
authorization refinement), that check must remain tolerant of unregistered devices, or it will
regress into a deviation from upstream's just-confirmed intent.
