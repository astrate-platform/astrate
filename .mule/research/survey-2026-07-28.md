# Survey — cross-project gap analysis (2026-07-28)

Sources: Astrate codebase/docs, mule queue history, upstream `astarte-platform`
0da8336 (post-v1.4.0-rc.2), upstream `atomvm/AtomVM` 0220c78. Each claim below cites a
specific file, path, commit, or upstream doc section.

Incremental note: the 2026-07-27 survey was against v1.4.0-rc.2. Upstream has moved
significantly since then — 45+ commits, primarily the key agreement / encrypted endpoints
subsystem. Astrate has also moved (M12-07 lttb, M12-08 NATS/HTTP forwarder, WATCH path
measurement). This survey focuses on material changes while carrying forward unresolved
gaps.

### Key agreement topic — gap now widened

The 2026-07-27 survey noted the `/<realm>/<device_id>/control/keyAgreement` topic was
"reserved and routed correctly, but the handshake protocol is not yet implemented" in both
upstream and Astrate. **This is no longer true.** Upstream has implemented the full key
agreement protocol (see Source 3 below). Astrate's broker (`internal/broker/aclhook.go`)
does not publish-allow this topic, and the engine has no handler for it. The gap has shifted
from "both sides aligned in not supporting it" to "upstream supports it, Astrate does not."

### Encrypted endpoints — entirely new upstream subsystem

Upstream now has two encryption layers that Astrate does not implement:

1. **Transport encryption**: After key agreement, server-to-device payloads on encrypted
   endpoints are wrapped in COSE Encrypt0 messages using the per-device shared symmetric key.
2. **At-rest encryption**: Device data written to encrypted endpoints is encrypted with
   per-write DEKs wrapped under a realm-level KEK (via OpenBao Transit Engine). New DB
   columns `encryptedblob_value` and `encrypted_dek` in properties and datastream tables.

Astrate has zero references to key agreement, COSE, DEK, KEK, or encrypted endpoints
(`grep -ri "key_agreement\|coise\|DEK\|kek\|encrypted_endpoint" internal/` returns nothing).

### New upstream error names (since v1.4.0-rc.2)

The key agreement implementation added five new error names to `control_handler.ex`:

- `key_agreement_transition_error` (lines 210, 229, 357)
- `key_agreement_error` (line 256)
- `secret_hash_error` (line 299)
- `hash_ok_error` (line 382)
- `exchange_failed_error` (line 639)

None of these are in the Dashboard v1.2.2 validated set (`errorname.go:6-22`). They are
all key-agreement-specific errors for a feature Astrate does not implement, so the practical
risk is low today — but if the Dashboard is upgraded or Astrate implements key agreement,
these names need to be mapped.

### Missed finding: `unset_not_allowed`

The 2026-07-27 survey missed this error name. Upstream `data_handler.ex:157-165` emits
`error_name: "unset_not_allowed"` when a device tries to unset a property with
`allow_unset: false`. This is not in the Dashboard v1.2.2 validated set. It is a real
operational error that can surface to Channels consumers. `internal/engine/triggers/errorname.go`
does not map any Astrate reason to this name.

### Upstream doc lag

`080-mqtt-v1-protocol.md` line 174 still says the key agreement topic "is not yet
implemented" — but the code clearly implements it (30+ commits since v1.4.0-rc.2). This is
a doc lag, not an Astrate gap, but it means the doc cannot be trusted as a source of truth
for the key agreement feature's status.

### Code-vs-docs disagreement

None found beyond the doc lag noted above. The frozen docs (`DESIGN.md`, `ROADMAP.md`) and
the code remain consistent.

## Source 3 — upstream `astarte-platform` (0da8336, post-v1.4.0-rc.2)

### Key agreement implementation (the major change)

45+ commits since v1.4.0-rc.2, primarily in `apps/astarte_data_updater_plant/`. The key
agreement protocol is now a complete implementation:

**State machine** (`HandshakeState`): 4 states — `:uninitialized`, `{:handshake_started, data}`,
`{:established, data}`, `{:failed, reason}`. Stored per-device in `encrypted_endpoints_key`.

**Key suites**: X25519 (suite 1, default) and ECDH P-256 (suite 0), both with HKDF-SHA256
and AES-256-GCM.

**MQTT message flow** (all CBOR-encoded on `<realm>/<device_id>/control/keyAgreement/<type>`):

| Topic | Type | Direction | Purpose |
|-------|------|-----------|---------|
| `/0` | InitExchange | Device → Astarte | `[seq_num, key_type, cose_key, hkdf_salt]` |
| `/1` | ExchangeResp | Astarte → Device | `[seq_num, cose_key]` |
| `/2` | SecretHash | Either | `[seq_num, sha256(shared_secret)]` |
| `/3` | HashOk | Either | `[seq_num]` |
| `/4` | ExchangeFailed | Either | `[seq_num, error_code, error_msg]` |

**Key derivation**: ECDH → HKDF-Extract (32-byte salt) → HKDF-Expand (info `"astarte-kdf"`)
→ 32-byte AES-256-GCM key. Stored as `COSE.Keys.Symmetric` in the `devices.shared_secret`
column.

**Encrypted endpoints**: Two layers:
1. **Transport**: COSE Encrypt0 wrapping of server-to-device BSON payloads using the
   per-device shared key.
2. **At-rest**: Per-write DEKs generated via OpenBao Transit, wrapped under realm KEK, stored
   in new `encryptedblob_value` and `encrypted_dek` DB columns.

**New DB migrations**: `0022_add_encrypted_to_individual_properties.ex`,
`0023_add_encrypted_to_individual_datastreams.ex`.
