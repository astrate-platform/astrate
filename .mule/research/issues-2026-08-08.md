### key-agreement-protocol
Title: Handle the `<realm>/<device_id>/control/keyAgreement` CBOR topic
Scope: mule-spec
Body:
Carried forward unchanged from `issues-2026-08-07.md` (re-grep-confirmed: only
the ACL deny comment `internal/broker/aclhook.go:65` and its test
`aclhook_test.go:53`). Upstream has implemented the full ECDH key agreement
protocol since v1.4.0-rc.2: a 5-message CBOR handshake over `keyAgreement/0`
through `/4` (`InitExchange`, `ExchangeResp`, `SecretHash`, `HashOk`,
`ExchangeFailed`), X25519 (suite 1, default) and ECDH P-256 (suite 0), a 32-byte
AES-GCM key derived via HKDF and persisted in `devices.shared_secret`, since
`5047681` encrypted at rest with the realm KEK. Since `208bfdb` the key status is
derived at session setup from DB presence (`:established`/`:uninitialized` in
`queries.ex`) and gates payload decryption — so this candidate is now also the
precondition for the COSE Encrypt0 data path below, not just the at-rest layer.
The fix and verification remain exactly as written on 08-01: (a) allow the topic
in the broker ACL for the device's own base, (b) decode the 5 CBOR message types,
(c) implement the state machine, (d) derive and persist the shared secret, (e)
emit the upstream error names on failure; verify with a T3 handshake test and an
invalid-InitExchange test asserting `key_agreement_error`. Prerequisite for
`encrypted-endpoints` below.

### encrypted-endpoints
Title: Implement encrypted endpoints (DEK/KEK at-rest encryption, COSE Encrypt0 transport both directions, parameter-aware)
Scope: mule-spec
Body:
Carried forward from `issues-2026-08-07.md` (unchanged; upstream `f65bda5d`
did not touch the subsystem). Astrate has zero DEK/KEK/COSE references (`git
grep -i "dek\|kek\|cose\|encrypted" origin/main -- internal/` matches only the
CA-private-key comment `internal/store/crypto.go:15` and the `fakeKeys`/`KeySource`
test doubles — the feature is absent). Upstream has two encryption layers for
mappings with `encrypted: true`: (1) at-rest DEK/KEK wrapping via Astarte
Secrets, stored in the `encryptedblob_value`/`encrypted_dek` columns, with the
per-device shared secret encrypted under the realm KEK; (2) **COSE Encrypt0**
transport using the key-agreement shared secret — confirmed as the wire format
on both directions: the appengine read path encrypts with
`EncryptedMessages.encrypt` (`device.ex:311`) and, since `208bfdb`, the DUP write
path decrypts with `EncryptedMessages.decrypt` before BSON decoding
(`data_handler.ex` `maybe_decrypt_payload`). The COSE Encrypt0 message is a
12-byte random IV plus the AES-GCM ciphertext, `alg` taken from the handshake
symmetric key (`:aes_128_gcm`/`:aes_256_gcm`), plaintext is the BSON payload
(`libs/astarte_secrets/lib/astarte_secrets/encrypted_messages.ex`). Rule: if the
current interface has any encrypted mapping, the whole message payload is
encrypted (`payload_encryption_enabled?`). Both sides use the **mapping's
endpoint** as the encryption-context path (parameter-aware via
`Value.path_matches_endpoint?`), which is what allows an encrypted mapping on
`/%{some_param}/encryptedValue`. Failure modes pinned: write side
`key_agreement_error` (no established key) and `decryption_error` (bad decrypt),
both a hard disconnect today (upstream TODO softens later); read side
`device_not_ready_for_encryption` when `devices.shared_secret` is nil. The fix:
(a) encrypted-value columns on properties/datastream tables, (b) a secrets
library for DEK generation/wrapping and shared-secret encryption, (c) COSE
Encrypt0 encrypt/decrypt with the mapping-endpoint (parameter-substituted)
context, (d) encrypt on write when the interface has an encrypted mapping,
decrypt before BSON decode, (e) decrypt on read. Verification: a T3 test with an
encrypted endpoint — including one on a parametrized path, per the upstream
fixture shape — asserting values store encrypted and decrypt on read, a COSE
Encrypt0 fixture round-trips byte-identically, and the failure modes emit
`key_agreement_error`/`decryption_error` (write) and
`device_not_ready_for_encryption` (read). Follows `key-agreement-protocol`.

### empty-cache-error-triggers
Title: Fire device_error triggers on `control/emptyCache` resend failure, matching upstream's error_name split
Scope: mule-spec
Body:
New — upstream `d8592091` (#2119, CHANGELOG `1.3.3` Unreleased). On
`control/emptyCache` property resend, upstream now fires a device_error trigger
with a distinct name per failure class and **ends the session** (clean session,
hard disconnect): `interface_loading_failed` when an interface fails to load,
`resend_interface_properties_failed` when sending the properties to the device
fails, `empty_cache_error` (with the reason in `extra_error_metadata`) for
anything else (`control_handler.ex:962-1069`, `device.ex:427-431`). Previously
both resend failures were mis-reported as `resend_interface_properties_failed`.
Astrate's `handleEmptyCache` (`internal/engine/control.go:57-74`) has no failure
surface: `resendServerProperties` skips unresolvable interfaces and un-
rehydratable values loudly (`control.go:151-167`), store errors retry with
shard-parking and are acked+logged on permanent failure (`introspection.go:135`)
— no device_error trigger is ever fired and the session is never ended, so a
trigger on `resend_interface_properties_failed`/`empty_cache_error` (both
already in the Dashboard validated set, `errorname.go:20-21`) can never fire,
and a device would keep retrying a resend upstream would terminate. Design
decision required before implementation: Astrate's skip-loudly behaviour is
deliberate robustness (a deleted interface mid-flight should not kill the
session) and conflicts with upstream's fail+disconnect; decide whether to adopt
upstream's semantics, diverge with a documented COMPATIBILITY.md note, or a
hybrid (skip quietly on the row, trigger only on total failure). Fix once
decided: emit the trigger on resend failure via the existing trigger path and
either clean-session (upstream parity) or document the divergence.
Verification: a T2/T3 test asserting a device_error trigger with the correct
error_name fires on an emptyCache resend failure.

Scope: mule-line
Body:
Carried forward from `issues-2026-08-07.md` (re-grep-confirmed against
`origin/main`: `handleCapabilities` in `internal/engine/capabilities.go:28`
still calls `e.reject` on both decode and validate failure — lines 31 and 36 —
and keeps the connection; `malformed_capabilities_message` is absent, only
`capabilities_payload_invalid` exists at `internal/engine/data.go:50`). Upstream
forcefully disconnects the device on a malformed capabilities message
(`080-mqtt-v1-protocol.md:125-128`), leaving stored values unchanged, and fires a
device_error with `error_name: "malformed_capabilities_message"`
(`capabilities_handler.ex:74-81`, `error.ex:79-87`,
`force_disconnection` in `device.ex:322-347`). Astrate's reject path fires a
device_error carrying the fallback `interface_loading_failed` (the real reason

Fix and verification unchanged from 08-01: add a `Disconnect` method to the
engine's `BrokerPort`, call it on the malformed path, map
`capabilities_payload_invalid` → `malformed_capabilities_message` in
`errorname.go`; T2 test asserting session termination + the correct error_name.
Secondary note (also unchanged): upstream persists capabilities per device
(`090-database.md:123-129`), Astrate keeps them in-memory and session-scoped —
record as a documented divergence in `docs/COMPATIBILITY.md` if not persisted.

### unset-not-allowed-mapping
Title: Fix `unset_not_allowed` error name mapping to match upstream
Scope: mule-line
Body:
Carried forward from `issues-2026-08-07.md` (re-grep-confirmed: `errorname.go:62`
still maps `"unset_not_allowed"` → `"unexpected_value_type"`). When a device tries
to unset a property with `allow_unset: false`, Astrate's decoder
(`pkg/payload/payload.go:68-69`) returns `ReasonUnsetNotAllowed`; the engine
rejects with reason `"unset_not_allowed"` and `errorname.go` maps it to
`"unexpected_value_type"`. Upstream emits the literal error name `"unset_not_allowed"`
(`data_handler.ex:255-260`), so the Dashboard/channels consumer sees a different
name than upstream would send for the same rejection. The fix: change the mapping
in `errorname.go` from `"unset_not_allowed": "unexpected_value_type"` to a
pass-through. `unset_not_allowed` is not in the Dashboard v1.2.2 validated set,
so the Dashboard discards the event either way — but the emitted name then matches
upstream's, which is the parity contract. Verification: a T1 test asserting
`UpstreamErrorName("unset_not_allowed")` returns `"unset_not_allowed"`; update the
existing test at `errorname_test.go` that expects the corrected value.

### bson-null-value-acceptance
Title: Verify whether a BSON-null individual value must be accepted (upstream `4789d047`)
Scope: mule-line
Body:
New — upstream `4789d047` restored type validation so a `nil` individual value
passes validation (`:ok` in `data_handler.ex` `validate_value_type`). Astrate's
BSON decoder has no `bson.TypeNull` case in `decodeBSONValue`
(`pkg/payload/bson.go`), so `{v: null}` for a non-nullable mapping is rejected as
`ReasonTypeMismatch` → `unexpected_value_type`. Low confidence this is a real
gap: the official SDKs encode unset as the empty payload, not `{v: null}`, and no
upstream test drives a null document through the data path — but the acceptance
clause is deliberate (it was part of the restored behaviour). The fix, if the
verification finds a sending path: accept `bson.TypeNull` for individual
mappings as an explicit nil (or reject it loudly with a documented divergence);
otherwise record the divergence in `docs/COMPATIBILITY.md`. Verification: check
the upstream SDK encode paths (Go/Rust/JS) for any `{v: null}` emission; if none,
add a one-line comment to `bson.go` documenting the deliberate divergence, no
behaviour change.
