## Source 3 — upstream `astarte-platform` (`029c630f`, moved 2026-08-06)

`git log 85c05c67..029c630f` is exactly two commits, both landed 08-06. Neither
touches `doc/` and neither adds a CHANGELOG entry. Together they complete the
**payload transport half** of the encrypted-endpoints subsystem: the write side
(device → DUP) now decrypts, the read side (appengine → device) was already
encrypting and gets a parameter fix. The handshake half (keyAgreement) was
already in place.

### `208bfdb` — chore(dup): decrypt payloads incoming on encrypted endpoints (#2103)

The DUP's `DataHandler` now decrypts incoming device payloads before BSON
decoding:

- `apps/astarte_data_updater_plant/.../core/data_handler.ex` — a new
  `maybe_decrypt_payload` step runs **before** `decode_bson_payload`. If the
  current interface has any mapping with `encrypted: true`
  (`payload_encryption_enabled?`), the whole message payload is expected to be a
  **COSE Encrypt0** message (`Astarte.Secrets.EncryptedMessages.decrypt`) using
  the shared secret derived during the key-agreement handshake
  (`context.state.shared_secret`). The decrypted bytes then feed the normal BSON
  decoder. The old commented-out ad-hoc AES-GCM `iv+tag+ciphertext` decrypt code
  is deleted.
- Two failure modes, both currently a hard disconnect (`ask_clean_session: true`,
  with an upstream `# TODO consider whether to make it a soft error`):
  - shared key not established (`encrypted_endpoints_key != :established` for a
    bare-atom `:established` state) → error_name `key_agreement_error`
    (`data_handler.ex:488-503`);
  - `EncryptedMessages.decrypt` fails → error_name `decryption_error`
    (`data_handler.ex:504-521`).
- `apps/astarte_data_updater_plant/.../queries.ex` — on session setup, the key
  status is derived from the DB: if `devices.shared_secret` is present it is
  `:established`, else `:uninitialized`. So "established" is now a real,
  persistable precondition, not just handshake-local state.
- Tests (`data_handler_error_test.exs`) add generated interfaces with encrypted
  mappings and assert `{:discard, :key_agreement_error, ...}` and
  `{:discard, :decryption_error, ...}`; the test harness encrypts generated
  plaintext with `EncryptedMessages.encrypt`.

The wire format is COSE Encrypt0 (`libs/astarte_secrets/lib/astarte_secrets/encrypted_messages.ex`):
12-byte random IV, `alg` from the symmetric key determined during the handshake
(`:aes_128_gcm` or `:aes_256_gcm`), protected header only carries the IV.

### `029c630` — fix(appengine): Handle parameters on encrypted endpoints (#2120)

- `apps/astarte_appengine_api/.../device/device.ex:348` — the server→device
  encrypt path now passes `mapping.endpoint` (not the raw requested `path`) as
  the encryption-context path to `maybe_encrypt_value`, matching the DUP-side
  change from #2112.
- `.../device_reading_v2_test.exs` — the encrypted-mapping check now uses
  `Value.path_matches_endpoint?` instead of a prefix string comparison, and the
  fixture endpoint becomes `/%{some_param}/encryptedValue`. This is the
  parameter-awareness the previous survey flagged as the #2112 consequence,
  confirmed on the read side too.

### Everything else upstream

Unchanged since `85c05c67`. Two notes, neither new:

- The protocol doc still says the keyAgreement handshake is "not yet implemented"
  (`doc/pages/architecture/080-mqtt-v1-protocol.md:174-176`) while the code has
  been live for two 1.4.0-rc releases — a doc lag, not a code gap.
- `device_not_ready_for_encryption` is emitted by the appengine **read** side
  (`.../device/queries.ex:940`) when `devices.shared_secret` is `nil`; the DUP
  **write** side now emits `key_agreement_error` for the same underlying state.

## Source 4 — parity gaps (updated topology)

No gap closed, no new gap opened. The two commits *refine an open gap*: the
`encrypted-endpoints` candidate now has a pinned wire format (COSE Encrypt0, not
the earlier ad-hoc scheme) and a real precondition chain. Updated topology:

| Area | Upstream behaviour | Astrate status | Reference |
|---|---|---|---|
| **Encrypted endpoints — COSE Encrypt0 both directions** | Any interface with an encrypted mapping carries a COSE Encrypt0 payload (12-byte IV, handshake `alg`); DUP decrypts before BSON decode; appengine encrypts on read with `mapping.endpoint` as context (parameter-aware) | Entire subsystem absent (`dek\|kek\|cose` matches are false positives) | `208bfdb`; `029c630`; `encrypted_messages.ex`; 08-06 survey |
| **Encrypted endpoints — failure modes** | Write side: `key_agreement_error` (no established key) / `decryption_error` (bad decrypt), both hard-disconnect (upstream TODO to soften); read side: `device_not_ready_for_encryption` when no shared secret | Not implemented; no such error names in `errorname.go` | `data_handler.ex:488-521`; `queries.ex:940` |
| **Key agreement protocol** | CBOR handshake on `control/keyAgreement/0..4`; shared secret persisted, encrypted at rest; key status `:established`/`:uninitialized` derived from DB presence | Not implemented; ACL deny + comment | `aclhook.go:65`; `aclhook_test.go:53` |
| **Capabilities: malformed handling** | Force-disconnect + `error_name: "malformed_capabilities_message"` | `e.reject` fires device_error, keeps connection, falls back to `interface_loading_failed` | `capabilities.go` `handleCapabilities`; `data.go:50` |
| **Capabilities: persistence** | DB-persisted per device | In-memory, session-scoped | 08-06 survey §4 |
| **`unset_not_allowed` error_name** | Emitted literally by upstream | Mapped to `unexpected_value_type` | `errorname.go:62` |
| **Group WATCH authz paths** | `groups/<name>/<interface><match_path>`, `groups/<name>` | Not measured (no group in realm); #17 | `COMPATIBILITY.md` deviation 1 |
| **`write_on_server_owned_interface` / `value_size_exceeded` error_names** | Emitted by upstream; threshold unclear for size | Mapped but unverified; #18/#19 | `COMPATIBILITY.md` deviation 1 |
| **Dormant data trigger types / group-scoped triggers** | Evaluated upstream | Accepted, never evaluated; #20 / tied to #17 | `match.go` |

The largest open subsystem is still key-agreement + encrypted-endpoints. Upstream
has now completed the full loop (handshake → shared secret → COSE Encrypt0
payloads both directions → at-rest DEK/KEK); the Astrate candidate must specify
the COSE Encrypt0 format explicitly so a future implementation matches the wire
rather than the earlier ad-hoc scheme. This is an update to the existing
candidate, not a new gap.
