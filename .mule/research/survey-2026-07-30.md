## Source 3 — upstream `astarte-platform` (5047681, +1 since 0da8336)

### Shared secret now encrypted at rest with realm KEK

Commit `5047681` (feat(dup): Encrypt device shared secret, 2026-07-29) changes how the
per-device shared secret is persisted after key agreement:

| Before (0da8336) | After (5047681) |
|---|---|
| `control_handler.ex` saves `Symmetric` key as-is | Encrypts `symmetric_key.k` via `Secrets.encrypt_with_kek/2` before save |
| `AppEngine.Device.Queries.get_shared_secret` returns raw key | Decrypts via `Secrets.decrypt_with_kek/2` on read |
| `DataUpdater.Queries` returns stored raw key | Decrypts in `maybe_decrypt_shared_secret/2` when loading device stats |
| No realm KEK needed at test setup | Tests call `Secrets.create_realm_kek/1` and stub `encrypt_with_kek`/`decrypt_with_kek` |

The new `astarte_secrets` functions (`encrypt_with_kek`, `decrypt_with_kek`) wrap existing
OpenBao Transit encrypt/decrypt calls using the realm's KEK (fetched by
`fetch_realm_kek/1`). They live in `Astarte.Secrets` alongside the existing
`generate_dek`/`encrypt_dek` infrastructure.

**Implication for Astrate**: This doesn't change the gap topology — Astrate still doesn't
implement key agreement or encrypted endpoints at all — but it adds a requirement to any
implementation: the shared secret must be encrypted with the realm KEK before storage, and
decrypted on read. The `Secrets` library API now has two additional top-level functions
(`encrypt_with_kek` and `decrypt_with_kek`) that any Astrate equivalent must match.
