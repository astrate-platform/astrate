## Source 1 — Astrate codebase and docs (main branch)

### TODO markers

Exactly one sanctioned `// TODO` remains, per `docs/ROADMAP.md` §0.1 rule 3:

### Trigger scope: accepted-but-never-firing conditions

`internal/engine/triggers/match.go:9-13` documents the boundary explicitly: these trigger types
compile successfully (install round-trips) but **never match and never fire**:

- `value_change` (line 30)
- `value_change_applied` (line 33)
- `path_created` (line 36)
- `path_removed` (line 39)
- `value_stored` (line 42)
- `device_empty_cache_received` (line 49)
- `interface_minor_updated` (line 61)

This is a deliberate v1 scope boundary, not a defect.

### Trigger types completely absent from Astrate (on main)

Upstream Astarte (doc `060-triggers.md`) defines these device trigger types that Astrate's main
branch has no constant for and never handles:

- `device_registered` — fires when a device is registered via Pairing API
- `device_deletion_started` — fires when device deletion begins
- `device_deletion_finished` — fires when device deletion completes

**Note:** `device_registered` has been implemented on the `mule/queue` branch (commit `89b1004`,
mule issue-12) but is not yet merged to main. The other two remain unimplemented.

### Group-scoped triggers not implemented

`internal/engine/triggers/match.go:11-12` notes group-scoped triggers compile but never match.
Upstream `060-triggers.md` documents `group_name` as a parameter on both device and data triggers.

### Protocol topics not implemented

**Capabilities** (`/<realm>/<device_id>/capabilities`): upstream MQTT v1 protocol doc
(`080-mqtt-v1-protocol.md` lines 17-18, 119-136) defines a BSON payload on this topic that sets
device capabilities (currently only `purge_properties_compression_format`: `"zlib"` or
`"plaintext"`). Astrate's broker ACL (`internal/broker/aclhook.go`) does not publish-allow this
topic; the engine does not parse it.

**Note:** Capabilities handling has been implemented on the `mule/queue` branch (commit `d670932`,
mule issue-16) but is not yet merged to main.

**Key Agreement** (`/<realm>/<device_id>/control/keyAgreement`): upstream MQTT v1 protocol doc
(`080-mqtt-v1-protocol.md` lines 22-23, 172-176) defines a CBOR-payload topic for a
cryptographic key agreement handshake. The protocol doc notes it is "reserved and routed
correctly, but the handshake protocol is not yet implemented" in upstream either. Astrate does
not handle this topic at all.

### Trigger action limitations

**Mustache templates**: upstream `060-triggers.md` lines 516-543 documents a
`template_type: "mustache"` action that renders HTTP request bodies from Mustache templates.
Astrate's trigger actions (`internal/engine/triggers/actions.go`) only implement the default
JSON action.

**`ignore_ssl_errors`**: upstream `060-triggers.md` line 234 documents this optional boolean on
HTTP actions. Astrate's trigger action config does not include it.

### Trigger delivery policies: prefetch_count

`docs/COMPATIBILITY.md` deviation 8 marks `prefetch_count` as not implemented. Upstream
`062-trigger_delivery_policies.md` line 52 documents this optional field.

**Note:** `prefetch_count` has been implemented on the `mule/queue` branch (commit `5ea4c1b`,
mule issue-15) but is not yet merged to main.

### `device_error.error_name` — unverified rows

`docs/COMPATIBILITY.md` deviation 1 (lines 121-124) states explicitly:

- `write_on_server_owned_interface` — unverified because the bench realm has no server-owned
  interface.
- `value_size_exceeded` — unverified because upstream accepted a 100 KB string without bracketing
  a size limit.

### Upstream error names outside the Dashboard's validated set

`internal/engine/triggers/errorname.go` carries the Dashboard v1.2.2 validated set (15 names).
Upstream `data_handler.ex` and `control_handler.ex` emit additional error names not in that set:

- `missing_required_mapping` (`data_handler.ex:294`)
- `unset_on_datastream` (`data_handler.ex:311`)
- `purge_properties_error` (`control_handler.ex:145`)
- `key_agreement_transition_error` (`control_handler.ex:211,230,358`)
- `key_agreement_error` (`control_handler.ex:257`)
- `secret_hash_error` (`control_handler.ex:300`)
- `hash_ok_error` (`control_handler.ex:383`)
- `exchange_failed_error` (`control_handler.ex:649`)
- `unexpected_internal_message` (`data_handler.ex:56` — internal handler)

**New since last survey (2026-07-27):**

- `decryption_error` (`data_handler.ex:453`) — upstream added this error name for decryption
  failures. Not in the Dashboard validated set. Not in Astrate's `errorname.go` mapping.
- `malformed_capabilities_message` (`capabilities_handler.ex:78`) — the capabilities handler
  emits this when a capabilities BSON message is malformed. Not in the Dashboard validated set.
  Not in Astrate's `errorname.go` mapping.

### Code-vs-docs disagreement

None found. The frozen docs (`DESIGN.md`, `ROADMAP.md`) and the code are consistent.
