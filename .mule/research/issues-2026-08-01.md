### key-agreement-protocol
Title: Handle the `<realm>/<device_id>/control/keyAgreement` CBOR topic
Scope: mule-spec
Body:
Upstream Astarte has implemented the full ECDH key agreement protocol since
v1.4.0-rc.2 (30+ commits, primarily `apps/astarte_data_updater_plant/`). The
protocol is a 5-message CBOR handshake over the control topics (`keyAgreement/0`
through `/4`): `InitExchange`, `ExchangeResp`, `SecretHash`, `HashOk`,
`ExchangeFailed`. It supports X25519 (suite 1, default) and ECDH P-256 (suite 0),
derives a 32-byte AES-256-GCM symmetric key via HKDF, and persists it in
`devices.shared_secret` as a COSE symmetric key struct — since `5047681`, encrypted
at rest with the realm KEK. **Status on `main` is unchanged from 07-30**: the broker
ACL (`internal/broker/aclhook.go`) denies the topic (now with a comment documenting
it as a deliberate non-implementation, matching upstream's old "reserved and routed"
status), and the engine has no handler for it — `grep -rn "key_agreement\|keyAgreement\|KeyAgreement"
internal/` matches only the ACL comment and its test. The fix: (a) allow the topic
in the ACL for the device's own base, (b) add a CBOR decoder for the 5 message
types, (c) implement the state machine (`uninitialized` → `handshake_started` →
`established` or `failed`), (d) derive and persist the shared secret (encrypted with
a realm-KEK equivalent, per upstream `Secrets.encrypt_with_kek`), (e) emit the
upstream error names on failure (`key_agreement_transition_error`,
`key_agreement_error`, `secret_hash_error`, `hash_ok_error`, `exchange_failed_error`).
Verification: a T3 test with a test device performing the full handshake; assert the
derived key matches upstream; publish an invalid `InitExchange` and assert
`key_agreement_error` is emitted. Depends on nothing else in this file, but is a
prerequisite for `encrypted-endpoints`.

### encrypted-endpoints
Title: Implement encrypted endpoints (DEK/KEK at-rest encryption and COSE transport encryption)
Scope: mule-spec
Body:
Upstream has two encryption layers for interface mappings with `encrypted: true`.
(1) **At-rest**: per-write Data Encryption Keys (DEKs) generated via OpenBao Transit
Engine, wrapped under a realm-level Key Encryption Key (KEK), stored in
`encryptedblob_value` and `encrypted_dek` columns (migrations `0022`/`0023`); since
`5047681` the per-device shared secret is likewise encrypted with the realm KEK
(`Secrets.encrypt_with_kek`/`decrypt_with_kek`). (2) **Transport**: server-to-device
payloads wrapped in COSE Encrypt0 using the per-device shared symmetric key from the
key agreement handshake. **Status unchanged from 07-30**: Astrate has zero references
to DEK, KEK, COSE, or encrypted endpoints (`grep -ri "dek\|kek\|cose\|encrypted_endpoint"
internal/` returns nothing). This is a major subsystem: DB schema columns, a secrets
library (OpenBao or a local equivalent) for DEK generation/wrapping and shared-secret
encryption, a COSE dependency, and changes to both the write path (DUP) and read path
(AppEngine). The fix: (a) add the encrypted-value columns to properties/datastream
tables, (b) integrate a secrets library, (c) encrypt on write when the mapping has
`encrypted: true`, (d) decrypt on read, (e) implement COSE Encrypt0 for
server-to-device transport. Verification: a T3 test with an encrypted endpoint; write
a value and assert it is stored encrypted; read it back and assert decryption
succeeds; write without a shared secret and assert `device_not_ready_for_encryption`
is emitted. Follows `key-agreement-protocol` — without a shared secret the transport
half is untestable.

### capabilities-malformed-disconnect
Title: Match upstream's malformed-capabilities handling (force-disconnect + `malformed_capabilities_message` error_name)
Scope: mule-line
Body:
The just-landed capabilities support (#16) diverges from upstream in a wire-visible
way on the error path. Upstream: a malformed capabilities message leaves previously
stored values unchanged and **forcefully disconnects the device**
(`080-mqtt-v1-protocol.md:125-128`), firing a device_error trigger with
`error_name: "malformed_capabilities_message"` (`capabilities_handler.ex:74-81`,
`error.ex:79-87`, `force_disconnection` in `device.ex:322-347`). Astrate's
`handleCapabilities` (`internal/engine/capabilities.go:31,36`) calls `e.reject`,
which fires a device_error and acks but **keeps the device connected**
(`internal/engine/data.go:377`); the reason `capabilities_payload_invalid`
(`data.go:50`) is not in `astrateToUpstream`, so the event carries the generic
fallback `interface_loading_failed` — misleading for a consumer, and the device can
retry forever. The fix: (a) add a `Disconnect` method to the engine's `BrokerPort`
(`internal/engine/engine.go:18-27` — today the concrete `broker.Broker.DisconnectDevice`
is only reachable from the realm deletion path), (b) call it from the malformed-
capabilities path, (c) map `capabilities_payload_invalid` → `malformed_capabilities_message`
in `errorname.go`. Secondary note: upstream persists capabilities per device
(`090-database.md:123-129`); Astrate keeps them in-memory and session-scoped
(`purgeCompressionFor`, `capabilities.go`) — acceptable for the normal flow where a
device re-publishes capabilities on connect, but worth recording as a documented
divergence in `docs/COMPATIBILITY.md` if not persisted. Verification: a T2 test that
publishes a malformed capabilities document and asserts the device's session is
terminated and a `DeviceErrorEvent` with `error_name` `malformed_capabilities_message`
is emitted; the existing `capabilities_test.go` assertions (rejects counters only)
stay green.

### unset-not-allowed-mapping
Title: Fix `unset_not_allowed` error name mapping to match upstream
Scope: mule-line
Body:
When a device tries to unset a property with `allow_unset: false`, Astrate's decoder
(`pkg/payload/payload.go:68-69`) returns `ReasonUnsetNotAllowed`; the engine rejects
with reason `"unset_not_allowed"` and `errorname.go` maps it to
`"unexpected_value_type"`. Upstream emits the literal error name `"unset_not_allowed"`
for this condition (`data_handler.ex:255-260`, re-verified against `5047681`), so the
Dashboard/channels consumer sees `unexpected_value_type` where upstream sends
`unset_not_allowed`. The fix: change the mapping in `errorname.go` from
`"unset_not_allowed": "unexpected_value_type"` to a pass-through. Note
`unset_not_allowed` is not in the Dashboard v1.2.2 validated set, so the Dashboard
will discard the event either way — but the name Astrate emits will then match
upstream's, which is the parity contract. Verification: a T1 test that asserts
`UpstreamErrorName("unset_not_allowed")` returns `"unset_not_allowed"`; the existing
test at `errorname_test.go:30` must be updated to expect the corrected value.
