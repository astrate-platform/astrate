## Source 3 — upstream `astarte-platform` (`f65bda5d`, moved 08-06/08-07)

`git log 029c630..f65bda5d` is 28 commits. Grouped by relevance:

### Wire-visible — `d8592091` fix(dup): stop remapping interface loading failed error (#2119)

On `control/emptyCache` the DUP resends all server-owned properties. Previously
both "the interface fails to load" and "sending the properties to the device
fails" were reported as `resend_interface_properties_failed`. The commit
separates them (CHANGELOG entry under `1.3.3` Unreleased):

- `.../core/device.ex` `resend_all_interface_properties` no longer swallows
  `:interface_loading_failed` and re-maps it — the true reason propagates
  (`{:error, reason} = error`, `device.ex:427-431`). It also fixes the iteration
  to filter mappings by `mapping.interface_id` (it was iterating every mapping
  of the descriptor set) and to halt on the first send failure, returning
  `:sending_properties_to_interface_failed`.
- `.../core/control_handler.ex` `resend_all_properties` (lines 962-1006) now
  dispatches the failure to one of three `Core.Error.handle_error` paths, each
  of which fires a **device_error trigger** and asks for a clean session
  (`ask_clean_session: true` — hard disconnect):
  - `:interface_loading_failed` → error_name `interface_loading_failed`
    (`interface_loading_error`, lines 1040-1052);
  - `:sending_properties_to_interface_failed` → error_name
    `resend_interface_properties_failed` (`sending_properties_error`,
    lines 1026-1038);
  - any other reason → error_name `empty_cache_error` with the reason in
    `extra_error_metadata` (`generic_error`, lines 1054-1069).
- Tests assert the `interface_loading_failed` trigger fires with the message
  discarded (`control_handler_test.exs`).

Astrate's `handleEmptyCache` (`internal/engine/control.go:57-74`) has no
equivalent: resend failures are retried (parking backpressure), acked+logged on
permanent failure, or skipped loudly per row; no device_error trigger is ever
fired and the session is never ended. See candidate
`empty-cache-error-triggers`.

### Wire-visible — `4789d047` fix(dup): restore correct type validation checks for incoming data (part of rc.3, forward-ported)

A regression that had been "allowing some incoming data to be incorrectly
rejected" is fixed; property-based tests added. `data_handler.ex`
`validate_value_type` now dispatches on the `%Mapping{}` instead of a bare
expected type:

- an individual value that is `nil` is accepted (`:ok`), not rejected;
- a `%Cyanide.Binary{}` (BSON 2.0-decoded binary) validates against the
  mapping's expected type;
- object-aggregated values validate each key through its own mapping's
  `validate_value_type`, so per-mapping special cases apply.

### Wire-visible — `aedc4148` fix(dup): ensure binaryblob data is correctly validated

A raw Erlang binary for a `:binaryblob` mapping (something that is *not* a
`%Cyanide.Binary{}` from the BSON decoder) is now rejected with
`unexpected_value_type`; only a BSON-decoded binary is accepted. Object-interface
values also delegate per mapping.

**Astrate already matches the binaryblob half**: its BSON decoder is a typed
raw-lookup (`pkg/payload/bson.go:120-125`) that accepts binaryblob only from
`bson.TypeBinary` (`BinaryOK()`), so a BSON string/null for a binaryblob
mapping already fails as `ReasonTypeMismatch` → `unexpected_value_type`. No gap.

**Astrate diverges on the nil half**: upstream accepts a `nil` individual value
(`:ok`) while Astrate's `decodeBSONValue` has no `bson.TypeNull` case and
rejects it as `ReasonTypeMismatch` → `unexpected_value_type`. Whether any
official SDK can actually send a `{v: null}` document is unverified — see
candidate `bson-null-value-acceptance` (low confidence, verification scope).

### Release notes — rc.3 (07-31) and rc.4 (08-06), both now on `master`

- `1.4.0-rc.3` (bf9437ca): [secrets] configurable Vault base namespace; [fdo]
  Vault support, chunked service-info; [dup] "avoid clogging AMQP queues when
  receiving invalid device messages" (`40e09e1f` bound consumer memory,
  `646202eb` stop re-queueing rejected messages, `4789d047` above), restored
  type validation.
- `1.4.0-rc.4` (171b83c4, dated 08-06): new `config` library with `_URL` /
  component-variable configuration for external services, applied to Vault
  (`ASTARTE_VAULT_*`) and FDO rendezvous (`PAIRING_FDO_RENDEZVOUS_*`); DUP RPC
  server reliability fixes (`5a8e3591`, `1657e508`, `a4a841ed`).

The two DUP robustness notes are parity *confirmations*, not gaps: Astrate's
reject-and-consume design (rejected messages are consumed, never re-queued) and
shard-parking backpressure (docs/DESIGN.md §1.4, §5.3) match upstream's
end-state for the clogging problem. The Vault/FDO config refactor is infra
Astrate has no counterpart for — not a parity item.

### Everything else

RPC supervisor cleanup/scalability, mississippi alignment, log-level env
vars, CI (ubuntu-24.04), FDO tests, secrets namespace URL fixes, `config`
coverage — no wire-visible parity impact. No `doc/` changes in the range; the
keyAgreement "not yet implemented" doc lag (`080-mqtt-v1-protocol.md:174-176`)
still stands.

## Source 4 — parity gaps (updated topology)

Two rows refined, two added. The 08-07 rows (encrypted endpoints, key agreement,
capabilities malformed handling + persistence, `unset_not_allowed`, group WATCH
authz, `write_on_server_owned_interface`/`value_size_exceeded`, dormant trigger
types) stand unchanged. Updated/additions:

| Area | Upstream behaviour | Astrate status | Reference |
|---|---|---|---|
| **emptyCache resend-failure error triggers** *(new)* | On `control/emptyCache` property resend failure, fires a device_error trigger with a distinct name — `interface_loading_failed` (interface fails to load) vs `resend_interface_properties_failed` (send to device fails) vs `empty_cache_error` (other) — and ends the session (clean session, hard disconnect) | Never fires a device_error trigger on resend failure: retries with shard-parking, acks+logs permanent failures, skips unresolvable rows loudly; `resend_interface_properties_failed`/`empty_cache_error` mapped but never emitted | `d8592091`; `control_handler.ex:962-1069`; `control.go:57-74`; `errorname.go:20-21` |
| **BSON-null individual value** *(new)* | A `nil` individual value passes validation (`:ok`) | `bson.TypeNull` has no decode case → `ReasonTypeMismatch` → `unexpected_value_type`; SDKs likely never send it (unverified) | `4789d047` `data_handler.ex`; `bson.go` `decodeBSONValue` |
| **binaryblob strictness** *(refined, no gap)* | Only BSON-decoded binary accepted for binaryblob; raw binary → `unexpected_value_type` | Already strict: typed `BinaryOK()` lookup rejects strings/null as type_mismatch | `aedc4148`; `bson.go:120-125` |

The largest open subsystem is still key-agreement + encrypted-endpoints
(carried). The empty-cache error-trigger row is the one genuinely new candidate
from this delta: Astrate already validates the error names in its Dashboard
set but its emptyCache path has no failure surface at all — so a trigger on
`resend_interface_properties_failed`/`empty_cache_error` would never fire, and
the device would keep retrying a resend that upstream would terminate.
