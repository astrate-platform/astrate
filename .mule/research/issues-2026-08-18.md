### upstream-error-names-new
Title: Add `decryption_error` and `malformed_capabilities_message` to the upstream error name set
Scope: mule-line
Body:
Upstream Astarte has added two new `error_name` values since the last survey (2026-07-27) that
are not in the Dashboard v1.2.2 validated set (`internal/engine/triggers/errorname.go`):

- `decryption_error` (`data_handler.ex:453`) — emitted when a decryption operation fails on
  incoming data. Not in the Dashboard `nke` array; would be discarded if surfaced through
  Channels.
- `malformed_capabilities_message` (`capabilities_handler.ex:78`) — emitted when a capabilities
  BSON message is malformed. Not in the Dashboard `nke` array; would be discarded if surfaced
  through Channels.

Neither error name appears in `Astrate's errorname.go` mapping. The fix: add both to
`upstreamErrorNames` (so they pass through the Dashboard validator) and add entries to
`astrateToUpstream` mapping any relevant Astrate reject reasons. Verification: update
`TestUpstreamErrorNameMapping` and `TestUpstreamErrorNameClosedSetInvariant` in
`errorname_test.go` to cover the new names.

### write-on-server-owned-verification
Title: Verify `write_on_server_owned_interface` error_name against upstream
Scope: mule-spec
Body:

an unverified guess. Upstream's `data_handler.ex:544` emits this error_name when a device
publishes on a server-owned interface. Astrate maps `ownership_violation` to this name

compare. Verification: a recording run against the self-hosted upstream that produces a fixture
row confirming the error_name; the fixture is committed and a conformance test asserts parity.

### value-size-exceeded-verification
Title: Verify `value_size_exceeded` error_name and upstream's size limit
Scope: mule-spec
Body:
`docs/COMPATIBILITY.md` deviation 1 (lines 123-124) marks `value_size_exceeded` as an
unverified guess because upstream accepted a 100 KB string without bracketing a size limit.
Upstream's `data_handler.ex:589` emits this error_name when value validation returns
`:value_size_exceeded`. The limit may be a Cassandra write constraint rather than an
application-level check, making it deployment-dependent. The fix: bisect payload sizes against
the self-hosted upstream to find the threshold (if any), record the error_name at the threshold,
and document the finding. Verification: a recording that captures the error_name at the
boundary and a test that asserts Astrate's `MaxPayloadBytes` config aligns with (or deliberately
differs from) the upstream limit.

### device-deletion-triggers
Title: Emit `device_deletion_started` and `device_deletion_finished` trigger events
Scope: design-decision
Body:
Upstream Astarte fires `device_deletion_started` when device deletion begins and
`device_deletion_finished` when it completes (`060-triggers.md:109-110`). Astrate performs
synchronous device deletion (`COMPATIBILITY.md` deviation 9) and emits neither event. Because
Astrate's deletion is synchronous and atomic (one transaction), there is no "in progress" state
to expose. The design decision: should Astrate emit both events in rapid succession (started then
finished, for trigger compatibility), emit only `device_deletion_finished` (the end state is the
only observable one), or skip both (documenting the divergence as deliberate)? This is blocked on
the mule/queue branch as a design decision. A device registered trigger that fires
`device_deletion_started` followed immediately by `device_deletion_finished` would satisfy
downstream consumers that check for the deletion lifecycle, but it adds complexity for
questionable value. This needs a human call before anything is coded.

### mustache-trigger-actions
Title: Decide whether to implement Mustache template rendering for HTTP trigger actions
Scope: design-decision
Body:
Upstream Astarte (`060-triggers.md:516-543`) supports `template_type: "mustache"` on HTTP
trigger actions, rendering the request body from a Mustache template with access to
`{{ realm }}`, `{{ device_id }}`, `{{ trigger_name }}`, `{{ event_type }}`, and all event
fields. Astrate currently accepts this configuration (`internal/engine/triggers/actions.go:46`)
but sends the default JSON envelope regardless (`actions.go:69`, noted as unsupported). The
decision: implement Mustache rendering (adds a Go Mustache library dependency, which ROADMAP
§0.1 freezes as pinned — this would need to be added), or document the divergence and keep the
default envelope. If implemented, verification would be a T1 test rendering a template with
known event fields and comparing the output byte-for-byte against an upstream-recorded fixture.

### group-scoped-triggers
Title: Decide whether to support group-scoped triggers in v1
Scope: design-decision
Body:
`internal/engine/triggers/match.go:11-12` notes group-scoped triggers compile but never match.
Upstream supports `group_name` on both device and data triggers (`060-triggers.md:121-123`),
restricting the trigger to members of a named group. Supporting this requires the engine to
check the device's group membership at trigger evaluation time, which means a DB lookup or a
cached group-membership map. The decision: implement group-scoped triggers in v1 (adds complexity
to the trigger matcher and a dependency on the groups table), or document the divergence? This is
related to the group WATCH paths issue — both need groups to exist in the bench realm for
verification. Deferred on the mule/queue branch pending bench data.

### group-watch-paths
Title: Measure and reconcile group WATCH authorization paths against upstream
Scope: mule-spec
Body:
`docs/COMPATIBILITY.md` deviation 1 (line 96) marks the group WATCH shapes
(`groups/<name>/<interface><match_path>` and `groups/<name>`) as "not measured, the realm having
no group." The bench upstream on the Legion has no group provisioned. This needs: (a) provision a
group in the bench realm with at least one device, (b) mint a narrow-`a_ch` token authorising a
WATCH on the group shape, (c) record the upstream's accept/reject against the recorded fixture
format (`test/conformance/upstream/channels.json`), (d) reconcile Astrate's
`Token.AuthorizesChannel` implementation. The group shapes rest on the same upstream function whose
device shapes M12 phase 06b confirmed, but they have never been observed. Verification: a
recording run against the self-hosted upstream that produces fixture rows for the group WATCH
shapes; the fixture is committed to `test/conformance/upstream/` and a test asserts Astrate's
behaviour matches.
