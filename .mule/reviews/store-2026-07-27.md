# Code review — `internal/store` (2026-07-27)

## What I read

Every `.go` file in `internal/store/` and every `_test.go` file in the same directory,
read largest-first. Plus `migrations/000002_metadata.up.sql` and
`migrations/000006_policies.up.sql` to verify FK definitions. Also searched all callers
of `store.New`, `Listen`, `ApplyGlobalRetention`, `DeleteRealm`, and `DeleteDevice` across
the repo to check usage patterns.

## What I found

### 1. Missing test: `trigger_policies` not verified in `DeleteRealm` cascade

**Where:** `realms_test.go` `CascadeDelete` subtest (line 149), `migrations/000006_policies.up.sql`

The `testRealms/CascadeDelete` test verifies that 9 tables are emptied after
`DeleteRealm`: interfaces, endpoints, devices, properties, individual_datastreams,
object_datastreams, groups, group_devices, triggers. But `trigger_policies` — added
in migration 000006 — is absent from the post-delete verification loop. The migration
defines `ON DELETE CASCADE` from `realms(id)`, so the cascade works at the database
level, but nothing in the test suite asserts on it. If someone were to change the
migration (e.g., remove CASCADE during a refactor), the test would not catch the
regression. This is a "rule that already exists but nothing asserts on" — the
recipe's highest-value category.

### 2. Missing test: `GetDeviceByAlias` lowest-ID-wins contract

**Where:** `devices.go` line 129-130 (comment), `devices_test.go` `AliasesAndAttributes` subtest

The comment at `devices.go:129` states: "If several devices share an alias the
lowest device ID wins; the API layer is expected to keep aliases unique per realm."
The SQL query (`ORDER BY id LIMIT 1`) enforces this, but no test proves it. The
existing `AliasesAndAttributes` test registers one device, sets an alias, and looks
it up — it never registers a second device with the same alias tag to verify that
the lowest ID is returned. This is a rule that silently rots if the query changes.

### 3. Missing test: `DeleteDevice` object-datastream cleanup

**Where:** `devices.go` `DeleteDevice` (line 443-449), `devices_test.go` `StatsAndDelete` subtest

`DeleteDevice` explicitly sweeps both `individual_datastreams` and
`object_datastreams` in its transaction (line 443-449). But the `StatsAndDelete`
test only inserts individual datastream rows and only verifies their removal
(devices_test.go:364-367). No test ever inserts object datastream rows for a
device and then deletes that device to prove the object rows are swept too. The
`DeleteRealm` test covers both tables, but `DeleteDevice` — which has its own
explicit sweep loop, separate from the realm cascade — does not.

## What I decided NOT to propose and why

- **`LoadRealmInterfaces` two-query design without transaction** (interfaces.go:266-321):
  The first query loads interfaces, the second loads endpoints. Between them, a
  concurrent `InstallInterface` or `DeleteInterface` could produce a `StoredInterface`
  with an empty `Endpoints` map. But this is inherent to the eventual-consistency
  design: the engine handles stale snapshots via the LISTEN/NOTIFY reload mechanism.
  Wrapping in a transaction would change the lock scope and is not warranted for a
  cache-rebuild path.

- **`SeriesQuery.tail()` / `Downsample` string concatenation for ORDER BY/LIMIT**
  (datastreams.go:191-200, 320-326): The `Limit` field is an `int` and `Descending`
  is a `bool`, so there is no injection risk. The pattern is slightly fragile (a
  future string-typed field could introduce injection) but is safe today and the
  surrounding code is clear.

- **`crypto.go` `decodeMasterKey` hex-before-base64 priority**: The 64-hex-char
  branch runs before base64 fallback. This is intentional — hex keys are the
  documented encoding. A key that is valid in both formats is decoded as hex, which
  produces the correct result.

- **Unbounded batch size in `AppendDatastreams`**: The batch comes from the engine's
  internal micro-batching, not from network input. The caller controls the size, and
  the `BatchSmoke10k` test exercises 10k rows. Not an injection or exhaustion vector.

- **`Listen` goroutine backoff semantics**: The backoff resets to `listenBackoffStart`
  after a successful connection+LISTEN, and stays there through transient
  `WaitForNotification` errors. This is correct — a previously-healthy connection
  warrants a short retry.
