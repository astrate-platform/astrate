## What I read in detail

I went through every non-test source file, largest first, and paid closest attention to the
concurrency seam (Router Submit/Drain fencing, the source pump / StopFlow drain ordering) and
to the two graph-validation paths (`Pipeline.Validate` and `topoOrder`), because those are
the rules that reject malformed pipelines at the API boundary.

## Findings

### 1. `Pipeline.Validate`'s no-source / no-sink rules are unreachable, and the tests that claim to cover them pass on the wrong path

`internal/flow/pipeline.go` rejects a pipeline with no source ("has no source block",
pipeline.go:148-150) and no sink ("has no sink block", pipeline.go:151-153). But these
branches can never fire:

- A graph that reaches the source/sink check has already passed the cycle check (the Kahn pass
  at pipeline.go:100-115 returns early on any cycle).
- Any acyclic graph necessarily has at least one source (in-degree 0) and at least one sink
  (out-degree 0). So once a graph is past the cycle check, `hasSource` and `hasSink` are both
  always true, and the two `if !hasSource` / `if !hasSink` error returns are unreachable.

The two test cases that claim to cover these rules, `"no source (all blocks have incoming
edges)"` and `"no sink (all blocks have outgoing edges)"` (pipeline_test.go:134-148,
150-163), both use the edge set `a→b, b→a` — a cycle. Validate returns the cycle error
(pipeline.go:113-115) before reaching the source/sink check, so the tests pass via the wrong
error path and never exercise the branch they name. They are `wantErr: true` for the right
reason but assert nothing about *which* error, masking that the branch is dead.

This is unguarded/honest-validation territory: the documented rule ("verify there is at least
one source and one sink", pipeline.go:45-46) claims a check that cannot ever trip. Either the
rule is vacuous and should be removed, or — if the intent is to reject a graph like a single
disconnected self-referencing node — it needs a real, cycle-independent formulation and an
assert-message test that reaches it.

### 2. Dead duplicated source/sink computation in `Pipeline.Validate` (clarity, mechanical)

Even before the reachability problem above, `pipeline.go:117-126` computes `hasSource`/
`hasSink` from `inDeg`/`outDeg`, and `pipeline.go:128-147` recomputes them from fresh
`inDeg2`/`outDeg2` and overwrites them — discarding the first result entirely. The first block
is dead code (the comment at pipeline.go:127 even documents the redundancy: "Re-compute
source/sink from original edges since topo sort zeroed inDeg"). Removing it is mechanical and
behaviour-preserving; the linter does not flag the overwritten-but-unread locals.

Items 1 and 2 are the same block of code viewed two ways: the whole source/sink validation is
both dead (computationally) and unreachable (by construction), and the tests that purport to
cover it actually cover a cycle. The natural single task is to make this rule either real or
gone, and to fix the two misleading test cases to assert the actual error.

## Decided not to propose, and why

- **The `onDrop` field on `flowMsg`** (router.go:79) is never assigned anywhere in the
  package, so `if fm.onDrop != nil` (router.go:140, 152) is a dead branch. Low-value cleanup;
  reads as a deliberate extension point for future ack-on-drop wiring. Not a queue line.
- **Router/Flow concurrency.** The Submit/Drain fencing (write lock retires lanes so no send
  is in flight; `quit` closes only once no Submit can start) is sound and well-commented; the
  source-pump vs StopFlow ordering (cancel pump → pumpWG.Wait → Drain → Stopper.Stop) is
  correct. No goroutine-with-no-exit, lock-across-I/O, or unbounded-from-network growth.
  (The `processOne` recover path is per-message and correctly isolated.)
- **Composite expansion / placeholder substitution** (composite.go, substitute.go) are
  carefully constrained (depth cap, cycle stack, config-key regex) and their tests are
  thorough. No missed-input growth worth a task.
- **Duplicated graph logic across `Validate` and `topoOrder`** (both compute in/out-degree
  and a Kahn order) is real redundancy but removing it touches two files, which the recipe
  forbids for a single task.

Finding little wrong in the router/flow core is the expected result; the pipeline.Validate
item above is the yield.
