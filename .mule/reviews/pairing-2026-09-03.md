## What I read in detail

I focused on the rate-limiting seam (§4.5 says "Rate limits: pairing endpoints
(per-IP and per-device)") because the doting design doc and the code diverge there in a
way that matters for CPU burn. I walked every handler in `http.go` and checked which ones
apply a `Limiter` and which ones reach `bcrypt.CompareHashAndPassword` via
`authenticateDevice` (service.go:367-398).

## Findings

### 1. Info + Verify do full bcrypt work with NO rate limit — unauthenticated CPU burn

**Where:** `internal/pairing/http.go` — `handleInfo` (line 197), `handleVerify`
(line 238); bcrypt compare via `authenticateDevice` (service.go:394).

`handleRegister` (line 106) and `handleCredentials` (line 154) both gate on a token-bucket
`Limiter` before doing any work. But `handleInfo` and `handleVerify` — the two device-auth
endpoints — check only `bearerSecret(r)` (any non-empty header passes) and then call
`Info`/`VerifyCredentials`, each of which runs `authenticateDevice` → a full
`bcrypt.CompareHashAndPassword` (cost 10, ~50-100ms of CPU).

Consequences:

- The `verify` endpoint is the SDK boot hot path that upstream expects to run on every
  reconnect (DESIGN.md:724-725), and `Info` is called on device bootstrap.
- An **unauthenticated** attacker needs only a client certificate to prove the server is
  reachable; any bearer string (valid or garbage) forces a bcrypt compare. With no per-IP
  throttle, they can hold a core busy at maximum rate. This is exactly the "blunt brute
  force" the design doc's §4.4/§4.5 rate limit exists to blunt — and the sibling
  `handleCredentials` endpoint, which does the *same* bcrypt work, is capped at
  burst-5/sec per IP+device. The two are wildly asymmetric for identical cost.

This is a real gap, not a theoretical one: the rate-limit test (`TestPairingHTTPRateLimit`)
covers only the credentials endpoint, so nothing asserts the intended behaviour for Info
and Verify.

**Proposed task:** add per-IP (and, like credentials, per-device) limiters to `handleInfo`
and `handleVerify`, and extend `TestPairingHTTPRateLimit` (or a sibling test) to assert that
a burst of fake-secret requests to `GET /devices/{id}` and `POST .../verify` returns 429.
Defaults can share the credentials limiter's parameters (1 req/s, burst 5) since the
legitimate load is a renewal per device per cert TTL.

### 2. (Note, not a task) `remoteIP` ignores proxy headers

`remoteIP` (http.go:340-348) keys rate limits on `r.RemoteAddr` only — no
`X-Forwarded-For`/`Forwarded`. DESIGN §5.1 explicitly supports a reverse-proxy deployment,
in which case every proxied request shares the proxy's IP and the per-IP throttles collapse
to one global bucket (both the brute-force dampener and, worse, a single shared budget that
legitimately distinct devices drain together). This is a config/design call, not a
tick-sized code fix, so I recorded it here rather than queueing it.

## Not proposed, and why (so the next run does not repeat this)

- **Info allowing inhibited devices while Credentials/Verify reject them** — intentional
  and documented (service.go:284-297, 282-302; inhibited may read info, only new creds and
  connections blocked) and asserted in `TestInfo`. Correct.
- **`Register` limit counting confirmed devices via `CountDevices`** — documented upstream
  parity ("the limit gates every registration attempt, secret rotations included",
  service.go:185-195), asserted in `TestRegisterLimit`. Correct.
- **`handleCredentials` double `Allow`** — consumes one token from the IP bucket and one
  from the per-device bucket, which is the intended per-IP *and* per-device throttle; the
  `||` short-circuit is fine. Correct.
- **`ca` package** — well-tested (TTL clamping, RSA challenge, serial uniqueness, Verify
  classification all present in `ca_test.go`); no gaps found.
- **`ratelimit.go`** — LRU-bounded keys, correct refill/cap; the `lru.New` size comment and
  the `elapsed == 0` early-out are both right. No change needed.
- **`writeServiceError` mapping** — every sentinel has an upstream-shaped response and the
  401-vs-403 deviation is explicitly frozen in ROADMAP. No finding.
- **Renames/reformatting** — none warranted; the code is idiomatic and internally
  consistent.

Finding little in most of the package was a correct result; the one genuine finding is the
rate-limit asymmetry above.
