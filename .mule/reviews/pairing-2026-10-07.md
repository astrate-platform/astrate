## What I found

1. **`burnBcrypt` ignores the configured `bcrypt_cost`** (proposed). The dummy-secret hash is
   generated once at package init with `bcrypt.DefaultCost` (service.go:94-100) and every auth
   failure burns a cost-10 compare against it (service.go:428-430), while real credentials use
   `cfg.BcryptCost` for both hash and compare (service.go:204, 407). `bcrypt_cost` is a real,
   documented, plumbed lever (config.go:106, main.go:152, configuration-reference.md:76 —
   default 10). An operator lowering it to 4 (renewal hot path) makes unknown-device / empty-hash
   / malformed-ID failures burn ~10× the work of a real compare: response latency reveals device
   existence, directly inverting the DESIGN §4.4 "constant-time-ish … uniform error" property this
   code exists to enforce.

2. **`Register` bypasses the injectable clock for the event timestamp** (proposed). Every other
   timestamp funnels through `s.now` (VerifyCredentials at service.go:333); the registration event
   uses literal `time.Now()` (service.go:222). The receiver (`e.HandleDeviceRegistered`,
   main.go:154) stamps the DeviceRegisteredEvent on the trigger bus, so a time-travel test cannot
   pin it and the bus sees wall-clock service time.

3. **`Unregister`'s malformed-ID branch is untested** (proposed). service.go:231-234 wraps a
   `deviceid.Parse` failure as `store.ErrNotFound`; `TestUnregister` (service_test.go:340) only
   exercises a well-formed unknown ID.

## What I decided not to propose, and why

- **Flow-C endpoints (`GET devices/<id>`, `POST .../credentials/verify`) are NOT rate limited.**
  Deliberate: DESIGN §4.4 and ROADMAP §4.4 scope the token buckets to `/credentials` + register.
  It is the same bcrypt-burn surface as the throttled ones but protected per DESIGN. Recorded,
  flag if the hardening checklist changes.
- **Register has no per-device bucket** despite ROADMAP §4.4's "per-IP *and per-device* … for
  `/credentials` + register". The hw_id comes from the request body and rotates freely, so a
  per-device bucket is trivially bypassable; and the endpoint is JWT-gated (`a_pa`). Not proposing
  a useless bucket; noted as spec wording that over-reaches the code.
- **`remoteIP` falls back to `netip.IPv4Unspecified()`** for unparseable `RemoteAddr` (http.go:356-366),
  collapsing all such clients into one IP bucket. Only reachable behind a unix-socket proxy;
  documented in the function comment. Not proposing.
- **`handleHealth` is unauthenticated and unthrottled** (http.go:78-81, 284-294). By design (#71 —
  FDO-flow devices probe it before holding credentials). Not proposing.
- **`register`/`unregister` unknown realm answers 404 device-not-found** via `writeServiceError`
  (http.go:326-327). Matches upstream parity for a missing realm; acceptable.
- **`VerifyCredentials` ENFORCE-LATEST parse-failure branch is dead** (service.go:350-354): the
  cert already parsed inside `ca.Verify` and succeeded, so `ParseCertificatePEM` cannot fail there.
  Harmless; not proposing a refactor of a defensive branch.
- **Rate limiter consumes two tokens per credentials request** (IP bucket + device bucket from one
  limiter, http.go:158). Correct two-dimension limiting, buckets stay in lockstep (same rate/burst,
  created together); `TestPairingHTTPRateLimit` already pins burst semantics. Not a bug.
- **`Register` counts every device row against the registration limit, rotations included**
  (service.go:188-198). The comment states this is deliberate upstream parity, not an accident; the
  http test (register_422_limit golden) pins it. Not challenging.

## Verdict

Well-kept package: the DESIGN-vs-code story is unusually complete and the test matrix (uniform
unauthorised, EXPIRED/INVALID/REVOKED classification, CA/openssl cross-check, LRU eviction, golden
envelopes) is dense. The one real gap is the timing-equaliser cost mismatch; the two tiny ones are
testability/coverage. Three lines appended.
