## What I found (worth proposing)

### 1. Group watches authorize against the group but deliver realm-wide — the membership is never consulted

**Where:** `internal/appengine/channels/room.go:36-40` (`watchEntry` has no
group field), `room.go:196-200` (the only delivery filter is
`w.deviceID != ev.DeviceID`, and for a group watch the top-level `device_id`
is empty), `ws.go:178-205` (`watchAuthPath` builds `groups/<name>/...`),
`triggers/match.go:374-396` (a group data trigger compiles with no device or
group scope because `group_name` lives at the payload top level, not inside
`simple_trigger`).

A client sending a group watch gets authorized against a *group-scoped* claim
(`WATCH::groups/probe/org.astrate.bench.Individual/value` on the wire, per the
conformance recording), but `Room.dispatch` then drops every event on the realm
whose interface/path/on matches — never filtering by whether `ev.DeviceID` is a
member of the group. `watchEntry.deviceID` is empty for a group watch, so the
one filter that exists is a no-op, and the compiled trigger has no group scope
either. Net effect: a token granted `groups/probe/...` receives data events from
**every** device in the realm publishing to that interface.

This is an unguarded security boundary, category 1. Upstream scopes group
triggers to group members; Astrate's group watch degrades to a realm watch
while the authorization claim still promises group scope. The fix needs a
group-membership resolver plumbed into `channels` (the package currently
knows only the `Bus`), membership resolved at Watch time and stored in
`watchEntry`, and delivery filtered by it. T1-testable with a fake resolver:
watch group probe, publish an event from a member and one from a non-member,
assert only the member's arrives. The group name cannot be handed to the
trigger compiler at present because upstream carries it at the payload top
level (recorded in channels.json), so the membership set must come from the
store/engine, not from `simple_trigger`.

### 2. A rejoin's new join_ref is documented but never pinned — and `handleJoin`'s rejoin path is not actually re-authorized

**Where:** `ws.go:284-291` (rejoin path updates `joinRef`, replies OK), the
comment at `ws.go:285-286` stating "server pushes must be tagged with the
current one", vs `pumpEvents` at `ws.go:403` which reads the current joinRef
per event.

No test drives a rejoin: `TestWireSession_*` joins once and asserts join_ref on
pushes from the first join, but nothing re-joins with a fresh ref and asserts
subsequent `new_event` frames carry it. The retagging rule exists and is
documented but rots unasserted (category 2, pure machine-checkable).

Relatedly, the comment at `ws.go:276-277` says "Upstream authorizes every join,
including a rejoin" — but the code only calls `AuthorizesChannel` in the
first-join branch; the rejoin path replies OK without re-checking. Outcome is
behaviourally identical today (a token is immutable for the session), so this
is a doc-vs-code mismatch, not an escalation: either move the authz check to
cover the rejoin branch too (harmless, matches the comment and upstream) or fix
the comment. Mechanical, but not witnessable by a test since claims cannot
change mid-session — propose as the small clarity fix.

## Decided NOT to propose, and why (so the next run does not re-derive them)

- **`handleUnwatch` swallows the payload unmarshal error** (`_ = json.Unmarshal`,
  ws.go:379) and replies OK even when nothing was removed. Phoenix replies ok to
  an unwatch of an unknown name; matching that is safest, and the only symptom
  today is an ok for a no-op. Not a boundary.
- **`dispatch` holds `memberMu` across the whole fan-out** (room.go:190-253).
  The send is a non-blocking `select`/default, so it never blocks and never
  deadlocks: `Member.Leave` serializes against it, and the close-while-sending
  hazard is exactly what the lock prevents. Contention is bounded by drop-fast
  semantics (§1.4). The `members` snapshot is redundant since the lock is held,
  but that is a rename-reformat-level itch, not a bug.
- **AddMember racing a bus-close retirement** (the join window between
  `reg.Join` and `AddMember`, ws.go:294-295 vs dispatch's defer at room.go:172-180)
  can leave a member in a room whose dispatcher exited. This only happens on
  `Bus.Close`, i.e. whole-server shutdown, where everything is dying anyway.
  Not a live-enough path to spend a tick.
- **No read limit / heartbeat timeout.** Aphasic clients holding a session
  forever is Phoenix's own model (client sends heartbeats; upstream doesn't
  kick either). Not a deviation, not worth proposing.
- **`session.ctx` = request context in `writeFrame`** (ws.go:439) is fine: the
  session loop owns the connection and `writeTimeout` bounds the write
  regardless. The DESIGN §1.4 slow-viewer contract is honoured and the 
  `writeTimeout`/mutex interaction is deliberate and commented.
- **Group watch + top-level `device_id` both present**: `watchAuthPath` takes
  the group branch and ignores the device, but `dispatch`'s `w.deviceID` filter
  would then silently narrow delivery to that one device. Upstream's changeset
  refuses the pair, so this is an already-impossible payload shape; finding #1's
  membership fix resolves it regardless.

The package is well-documented, the conformance rows are measured rather than
guessed, and the authz/refusal rows are pinned at both unit (`TestWatchAuthPath`)
and wire (`TestWireSession_*`) level. One security-scope gap and one missing test
is a proportionate yield for ~1,000 read lines.
