## What I found

### 1. Missing unit tests for pure helpers (category 2: rules nothing asserts on)

Four pure/near-pure helpers in this package have zero dedicated unit tests. They are exercised
only through integration tests (which require TimescaleDB). A regression in any of them would
only surface on the Legion Go; the Pi cannot catch it.

**`normaliseIfaceName`** (service.go:294-305): the collision key for interface names —
lowercases and strips hyphens. Called by `checkNameCollision`, which gates every install.
The integration tests cover it indirectly (collision tests in http_test.go), but an isolated
unit test would pin the exact normalization without needing a DB.

**`joinPEM`** (service.go:644-657): concatenates PEM keys with `\n` separators. Three code
paths (empty, single, multi). Integration test `ConfigAuth` exercises it but does not assert
the separator format or the empty case.

**`triggerErrorBody`** (http.go:268-285): builds the nested 422 envelope for trigger
validation errors. Called only from `createTrigger` handler. The integration tests compare
exact wire bodies but through the full HTTP stack; a unit test would pin the index-alignment
and empty-map substitution logic.

**`majorParam`** (http.go:338-345): parses `{major}` path segment, rejects negative values.
Only exercised through integration tests; a unit test would pin the -1 → 404 mapping.

### 2. No behavioural bugs found (category 1)

The package is defensively coded. Error sentinels are wrapped correctly, nil callbacks are
guarded, the invalidation-on-mutation contract is consistent (`interfacesChanged` for
interfaces, `triggersChanged` for triggers — both call `NotifyInterfacesChanged` because
triggers ride in the same engine snapshot, documented at service.go:503-511). `DeletePolicy`
has a theoretical TOCTOU between the trigger-reference check and the store delete, but the
store likely enforces referential integrity at the SQL level, making the service check a
friendlier error message layer rather than the sole guard. No fix needed.

### 3. What I decided NOT to propose

**`validationDetail` manual prefix matching** (http.go:562-568): uses
`msg[:len(prefix)] == prefix` instead of `strings.HasPrefix`/`strings.TrimPrefix`. It works,
it's readable, and a rewrite would be churn for no safety gain. Not proposing.

**Refactor `writeInterfaceError` / `writeError` duplication**: both handle overlapping error
sentinels but with different HTTP status codes and messages for the same sentinel (e.g.
`store.ErrInterfaceMajorNotZero` → 409 in writeInterfaceError, 422 in writeError). This is
intentional — the comment at http.go:351 says "Only the six interface handlers route here on
purpose — triggers and policies keep the generic writeError, so none of these details can leak
onto those surfaces." Changing this would be a refactor touching >2 files. Not proposing.

**`DeletePolicy` atomicity**: the list-then-check-then-delete is not wrapped in a service-level
transaction, but the store's `DeleteTriggerPolicy` likely has a FK constraint. The service
check provides a friendly error message. No fix needed at this layer.
