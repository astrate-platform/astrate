# Code review: internal/auth — 2026-09-14

## What I read

`internal/auth/claims.go` (204 lines), `middleware.go` (196 lines), `jwt.go` (139 lines),
`cache.go` (81 lines) in full, and all four test files in full
(`claims_test.go`, `jwt_test.go`, `cache_test.go`, `middleware_test.go`). Traced every
middleware caller across the surfaces (`cmd/astrate/main.go`, `internal/{pairing,realm,
appengine,housekeeping,flowapi}`) and the `internal/appengine/{stream,channels}` socket
handlers to confirm usage and claim semantics. `internal/auth` had no prior review file
(this is its first).

## Findings

This is a well-guarded package: the sentinel-error split, the PEM parse rules, the
key-rotation loop, the immutability that makes cache sharing safe, the
JOIN/WATCH-vs-REST a_ch difference, and the RELATIVE-path rules all have direct tests,
several pinned against recorded upstream behaviour. Two narrow rules and one brace branch
have no assertions at all; nothing is wrong or unguarded in the way category 1 means.

### 1. `iat` is not required/validated — zero coverage (jwt.go:104-105) — category 2

```go
// ... `exp` and `nbf` are honoured when present; `iat` is not required — upstream
// parity, docs/DESIGN.md §4.2
```

The comment pins a rule ("iat is not required") but the only token verified in every
test carries either future or absent `exp`/`nbf` and never a present-but-odd `iat`. The
parser options (`jwt.NewParser(jwt.WithValidMethods(...), jwt.WithTimeFunc(now))`) do not
add `WithIssuedAt`, so a token whose `iat` is *in the future* currently verifies. A
regression that begins validating `iat` (e.g. adding `jwt.WithIssuedAt`) would silently
break every token minted by a slightly-skewed clock with no test noticing. Fully
machine-checkable rule pin.

### 2. A validly signed token with *no* Astarte claims is 403, never 401 — zero coverage (middleware.go:149-151) — category 2

The status split is the point of the middleware: missing/unverifiable token → 401,
verified token that authorizes nothing → 403 (`TryAuthorize` → `Authorizes` → false →
`WriteForbidden`). Every existing test exercises 401 with a bad/unknown token and 403
with a token that *has* a claim but on the wrong surface (`narrowToken`). No test uses a
token with an entirely empty claims set, so a regression that turns "authenticated but
grant-less" into a 401 (or skips the forbidden path) would pass the whole suite.

### 3. `NewCache` size<1 fallback branch untested (cache.go:29-31) — category 2

```go
if size < 1 {
    size = DefaultCacheSize
}
```

Zero coverage; the branch exists purely so `lru.New` cannot panic. A regression that
drops the fallback and panics on `NewCache(0)` would pass every test.

## What I decided not to propose

- **The a_ch gate on the Astrate-native live socket matches the verb field as a regex
  against `GET`** (`internal/appengine/stream/ws.go:41` → `RequireRealm(ClaimChannels)`
  → `Authorizes(ClaimChannels, "GET", "socket")`). Consequence: the canonical upstream
  Channels grants `JOIN::.*`/`WATCH::.*` can never open the socket, while `.*::.*` — which
  the measured a_ch grammar says authorizes nothing on the Phoenix Channels surface —
  does. This *looks* like a category-1 inversion of the pinned a_ch rule, but it is
  deliberate and documented: the handoffs instruct minting REST-style a_ch for the stream
  socket ("App JWT for stream must use REST-style `a_ch` (`.*::.*`), not JOIN/WATCH",
  docs/handoff/pokemon-agent-memory.md) and `stream/ws_test.go:62` pins it as the accepted
  token. Re-litigating it needs a decision about what "authorized to connect" means on a
  room-less socket, which is Giulio's call, not a task. Flagged here so the next review
  does not re-derive it.

- **Bearer-tab separation divergence**: the upstream regex `~r/bearer\:?\s+(.*)$/i`
  accepts any whitespace, `bearerToken` (middleware.go:183) only cuts on a literal space,
  so a tab-separated `Bearer\t<token>` is 401 here but would parse upstream. No real
  client sends a tab there; would need a live upstream probe to confirm the claim and the
  payoff is nil. Not worth a tick.

- **`ErrNoKeyMatched` masks a disallowed algorithm** (jwt.go:132-137): golang-jwt wraps
  an unlisted-alg rejection in `ErrTokenSignatureInvalid`, so HS256/`none` attempts end as
  "token matches none of the realm keys". Cosmetically misleading sentinel in a package
  whose middleware swallows the error into a 401 with no logging — only the test suite
  could tell the two causes apart, and it currently just asserts rejection. Low value.

- **PEM re-parse + RSA verify on every failed attempt** (cache.go:70-75): failures are
  deliberately not cached (pinned by `TestCacheFailedVerificationNotCached`), so a replay
  of one bad token re-parses the key set each time. This is the standard don't-cache-
  failures trade-off, not a bug.

- **`NewCache`'s `panic` branch** (cache.go:35-37): unreachable — `lru.New` only errors
  for size < 1, which the fallback excludes. Not worth asserting.
