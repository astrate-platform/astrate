# Code review — `internal/realm` (2026-09-01)

## What I read

Every `.go` file in `internal/realm/` — `service.go` (491), `http.go` (318),
`policy.go` (17) — and every test: `http_test.go`, `dashboard_compat_test.go`,
`policy_test.go`. I also checked the store side of `ListTriggerPolicies`
(`internal/store/policies.go`) to confirm the ordering the service relies on, and
searched the tests for interface-lookup 404 coverage.

This is a small, well-commented package (Realm Management API §3.7). The
referential-integrity rules between triggers and delivery policies are already
covered by `TestPolicyReferentialIntegrity`, and the dashboard surface by
`TestDashboardCompat`. Most service methods are thin validated wrappers over the
store with correct upstream-shaped error mapping.

## What I found

### 1. `ListPolicies` is the only list method that does not sort its output

`internal/realm/service.go:379` returns `ps[i].Name` directly from the store. Its
three siblings all sort before returning: `ListInterfaces` (service.go:189),
`ListInterfaceMajors` (service.go:214), and `ListTriggers` (service.go:323).

It happens to be deterministic today only because the store's
`ListTriggerPolicies` orders by name (`internal/store/policies.go:66`). The service
contract for every other list method guarantees a sorted response regardless of
store order; `ListPolicies` silently depends on the store's internal ORDER BY. And
no test asserts on it — `TestDashboardCompat.Policies` installs exactly one policy.

Fix (mechanical, one line) plus a machine-checkable test that installs several
policies in a deliberately non-alphabetical order and asserts `GET /policies`
returns them sorted. Aligns the service with its siblings and pins the contract.

### 2. No test covers the 404 path for interface lookups

`ListInterfaceMajors` returns `ErrNotFound` for an interface name that has no
installed major (service.go:211-213), and `GetInterface` forwards the store's
`ErrNotFound` for an unknown major (service.go:225). The HTTP layer maps both to
404 (http.go `writeError`:302-303). Nothing asserts this: `TestRealmManagement`
only exercises the happy paths (`ListAndGet`, `MajorCoexistence`), and even the
interface-name endpoint has no unknown-name case.

A rule ("unknown interface/major is a 404, not 200 with an empty list") that
nothing asserts on. Small, cheap, fully machine-checkable — add 404 assertions to
`TestRealmManagement` for `GET /interfaces/<nonexistent>`, `GET
/interfaces/<name>/<no-such-major>`, and a 404 on a major that exists in no realm.

## What I decided NOT to propose and why

- **`DeletePolicy` swallows a trigger definition that won't unmarshal (`continue`,
  service.go:394-396)**: skipping a corrupt trigger would let a policy it references
  be deleted anyway. But `CreateTrigger` validates every definition through
  `triggers.Compile` (service.go:263) and `triggerPolicyRef` reads the same top-level
  `policy` key, so no trigger reachable through the API can land in the store
  unparseable at that shape. Unreachable defensive code; touching it would be
  churn without a reachable test.
- **`UpdateInterface` "stored interface does not parse" branch (service.go:140-143)**:
  defensive only — every stored definition was full-validated on install/update. If a
  corrupt row ever appeared, returning an error is the correct behaviour. Nothing to
  fix.
- **`SetAuthKey` stores one concatenated string, never populating the rotation list
  (service.go:441)**: matches upstream PUT semantics (replace the whole set) and the
  verifier splits concatenated keys; round-trips cleanly (`TestRealmManagement
  ConfigAuth` proves it). Not a bug.
- **`DeleteDevice` mapping a malformed device ID to 404 (service.go:83)**: the
  dashboard test explicitly asserts this upstream-device-404 envelope
  (dashboard_compat_test.go:126-134). Deliberate, tested.
- **`interfacesChanged`/`triggersChanged` swallow post-commit NOTIFY/invalidation
  errors (service.go:469-491)**: intended self-healing path, commented as such.
- **Policies deliberately not invalidating the engine snapshot (service.go:327-335)**:
  a documented, correct design decision (policies are unreferenced at create/delete;
  trigger mutations refresh). Covered by comment; not a gap.
