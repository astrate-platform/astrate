## What I found

### 1. Flow.setStatus called without lock (behaviour/unguarded) — `flow.go:157`

`Manager.StartFlow` calls `f.setStatus(FlowStatusFailed)` at line 157 outside any
lock. The comment on `setStatus` says "called under lock by the manager" but that
contract is broken in this path. Meanwhile `f.Status()` (line 87) reads `f.status`
under `f.mu.RLock()`. If a concurrent goroutine calls `f.Status()` while
`StartFlow` is setting the failed status on the same goroutine, this is a data
race.

The race is narrow — the flow is only visible to the caller of `StartFlow` at
that point, not yet in the manager's map — but the lock discipline is wrong and
a future refactor that exposes the flow earlier would make this a live race.

### 2. Pipeline.Validate dead-code + redundant recomputation (clarity) — `pipeline.go:117-152`

After the topological sort, `Validate` has a loop at lines 117-123 that checks
`inDeg`/`outDeg` but does nothing (the body is a comment saying "Re-check using
original degrees"). Lines 124-131 then check the same maps again. Then lines
133-152 recompute `inDeg2`/`outDeg2` from scratch and check those. The
inDeg/outDeg from the topological sort have been modified (zeroed by the sort),
so the checks at lines 124-131 are always true for every block in a cycle-free
DAG (every block ends at 0 inDeg after full topo sort). This is confusing dead
code.

### 3. Unchecked type assertion in dataWireScalar — `message.go:199-210`

`dataWireScalar()` handles `TypeBinary` and `TypeDatetime` with type assertions
but falls through to returning `m.Data` directly for the default case. If
`m.Data` is the wrong Go type for the declared `m.Type` (e.g. a `string` in an
`TypeInteger` message), the wire format will contain the raw Go value with no
error. This is not exploitable from network input (UnmarshalJSON validates), but
it means programmatic construction of a malformed FlowMessage silently produces
bad wire output. A brief `default:` branch with `// unreachable after
UnmarshalJSON` or an explicit check would document the invariant.

### 4. No tests for UnmarshalJSON error paths — `message_test.go`

The existing message tests only exercise happy-path round-trips. There are no
tests for:
- Unmarshal with a missing `"key"` field
- Unmarshal with `"type"` set to an invalid type string
- Unmarshal with `"type"` set to a map containing a non-string value
- Unmarshal with map data containing a field not present in FieldTypes (the
  field is silently copied as raw `any`)

### 5. Pipeline.Validate source/sink check against cycles is conflated — `pipeline.go:117-158`

The "no source" and "no sink" checks are supposed to catch pipelines where every
block has incoming (respectively outgoing) edges, which implies a cycle. But a
cycle is already detected by the topological sort (line 113-115). The source/sink
checks add a meaningful constraint beyond cycle detection (the pipeline must have
a block with no incoming edges AND a block with no outgoing edges), but the error
message "has no source block" could confuse a user whose real problem is a cycle
that also happens to lack sources. This is minor but the dead code in #2 makes
the whole section harder to reason about.

## What I decided NOT to propose

- **Router.Submit TOCTOU on `closed` flag**: Submit reads `r.closed` under lock,
  drops the lock, then sends on the channel. A concurrent Drain could close the
  channel between the unlock and the send, causing a panic. However, Drain
  already closes channels only after setting `closed=true`, and the panic is
  recovered by `processOne`. The send-on-closed-channel would actually panic in
  the caller (Submit), not in the lane goroutine. This is a real bug but
  fixing it requires either holding the lock during channel send (performance
  hit on the hot path) or changing Drain to not close channels (changing the
  semantics of lane drain). This is a design decision — flagged to Giulio in
  `for-giulio.md` instead of proposing a task.

- **Manager.StartFlow holds mu during graph/router construction**: This blocks
  all other Manager calls during construction. If NewBlockGraph or NewRouter
  becomes expensive, this is a problem. Currently they are cheap. Not proposing
  until there is a measured workload.

- **`flowMsg.onDrop` is always nil**: flowMsg is constructed in Submit with no
  onDrop callback, so the onDrop call site at lines 131 and 143 is dead code.
  Minor — the pattern is clearly designed for future use.

## Evidence

I wrote a small probe to confirm the setStatus race is real:

```go
// /tmp/flow-race-probe.go
// Launches concurrent Status() calls while StartFlow sets status.
// Confirms that setStatus is called without f.mu held.
```

Ran `go test -race ./internal/flow/...` — no race detected with current test
sequence because `StartFlow` completes before any concurrent `Status()` call.
The race is latent: it would surface if the flow were exposed to another
goroutine before `StartFlow` returns (e.g. via a channel or callback). The
contract ("called under lock") is broken, which is the finding.
