## What I found

One genuine behaviour bug, plus two small test gaps.

### 1. `RegisterDevice` silently clears `inhibited` on an unconfirmed device

`internal/store/devices.go:75-91`. The `ON CONFLICT ... DO UPDATE` sets
`status = 'registered'` unconditionally for any device with
`first_credentials_request IS NULL`. `SetDeviceInhibited` (devices.go:251-268)
sets `status = 'inhibited'` on *any* existing device — it does not require
`confirmed`. So an admin can inhibit a freshly registered, not-yet-confirmed
device, and the device's next re-registration flips it straight back to
`registered`, silently un-inhibiting it. In the pairing/engine layers an
inhibited device is blocked from new credentials and connections (§5.3 of
DESIGN.md), so this re-open is security-relevant, not cosmetic. Upstream keeps
its inhibit in a column registration never touches; Astrate folds the flag into
`status`, and this `SET` is the undesired side effect. Confidence: high on the
Astrate-internal contract, medium on exact upstream parity (worth confirming
against upstream on the Legion while the test runs there).

Rule is untested: the Lifecycle re-register cases (devices_test.go:42-75) cover
only registered → rotated and confirmed → 422; the inhibit round-trip
(devices_test.go:78-89) runs on a confirmed device. No case combines inhibit
with re-register.

### 2. `validatePipelineGraph`: two error branches untested

`internal/store/pipelines.go:51-64` rejects (a) a definition with zero blocks
and (b) a block with an empty name. `pipelines_validate_test.go` covers
acyclic / cyclic / unknown-block-ref / duplicate-name only. Pure-Go helper, no
DB needed, trivial machine-checkable addition.

### 3. `GetDeviceByAlias`: lowest-ID tie-break untested

`internal/store/devices.go:130-131` documents "if several devices share an
alias the lowest device ID wins", and the query implements `ORDER BY id LIMIT 1`.
`AliasesAndAttributes` (devices_test.go:222-267) only looks up a single device's
alias. Defensive rule (the API layer keeps aliases unique), but a documented
behaviour with no assertion.

## What I decided NOT to propose (and why)

- **`UpdateInterface` refusing an endpoint drop for a major-0 minor update**
  (interfaces.go:145-150): deliberate, documented, and already tested
  (interfaces_test.go:139-151). Whether upstream's major-0 relaxation should be
  mirrored is a compat-policy decision for Giulio, not a queue item; nothing in
  DESIGN.md contradicts the current code.
- **`AddGroupDevice` cross-realm group reports "group not found"**
  (groups.go:107-111): the SELECT guard means the message is correct for a
  missing group; a missing device already surfaces as device-not-found via the
  FK branch. Not a bug.
- **Perf (Downsample avg coalesce, per-row `validate()` in AppendDatastreams,
  GetDeviceByAlias jsonb build):** no nameable workload in reach of what is
  clearly a non-hot path; per the recipe, a `-bench` measurement task must come
  first and I have no evidence one is worth it.
- **`Listen` reconnect / backoff**: behaviour already pinned by the integration
  test `SurvivesBackendKill`.
- **Series boundary semantics, SeriesSpan, LatestIndividual,
  IndividualSnapshot, AliasValuesTaken:** all already asserted.
- **Missing JSON validation at store-create for triggers/policies:** the realm
  service validates before the store (service.go:419-457, 515-524); not a store
  gap.

## Verdict

Well-written package; the inhibit interaction is the one real find. Proposing
three lines (two `[legion]` for the DB-requiring store integration tests, one
container-free).
