## What I found (worth proposing)

The package is the best-covered in the repo: golden vectors captured from the
official Go SDK byte-compare against Astrate's re-encode, the sniff is fuzz-proven
non-colliding, every coercion edge in the table is asserted, and the decode side
never panics on garbage. I found **one wrong behaviour** and **one unpinned rule**:

1. **`jsonInt64` accepts fractional tokens that round onto an integer** (json.go:
   255-271). The ParseFloat fallback checks integrality on the *rounded* float, so
   within the documented-safety window |x| < 2^53 — where the very same comment
   (json.go:250-254) claims "the decimal→binary parse itself may round, silently
   corrupting the value" can never fire — fraction tokens whose neighbourhood has
   float64 ULP ≥ 1 (magnitude ≥ 2^52) land on an integral float and are accepted
   with the fraction silently dropped, and tiny fractions underflow to 0:
   - `{"v":4503599627370496.5}` → decoded as `4503599627370496` (no error)
   - `{"v":6000000000000000.9}` → decoded as `6000000000000001` (no error)
   - `{"v":5e-400}` → decoded as `0` (no error)
   Verified with a throwaway probe (see below). The stated rule is "Fraction or
   exponent forms are accepted only when integral" — `4503599627370496.5` and
   `5e-400` are not integers, so this is a coercion the code's own contract forbids,
   and it is silent. Fix: on the float fallback, verify the token is an *exact*
   decimal integer (`math/big.Rat` SetString + IsInt) before accepting; this keeps
   `5.0`, `1e3`, `0.5e1` accepted (all exactly integral) and rejects the two
   rounding cases as ReasonTypeMismatch. The plain-integer ParseInt fast path and
   the > 2^53 window check are unchanged. BSON is unaffected (longinteger from BSON
   accepts int64/int32 only, §2.6). Add the failing rows to `TestJSONProfile`.

2. **A malformed `t` on a non-explicit mapping is rejected, and nothing asserts
   it** (json.go:50-66). The facade's contract (payload.go:52-54) says a present `t`
   is "tolerated and ignored (upstream leniency)" when the mapping does not declare
   explicit_timestamp, but that tolerance only applies to a `t` that *parses*:
   `decodeJSONEnvelope` parses `t` before the facade knows the policy, so
   `{"v":1,"t":"yesterday"}` (explicit=false) is a ReasonBadTimestamp rejection, not
   an ignore. The valid-`t`-ignored case is pinned ("t ignored without explicit");
   the BSON twin ("t wrong type") is pinned at explicit=false too; only the JSON
   malformed-`t`-with-explicit-false side has no row — a no-op regression that
   implements "ignore a bad t on non-explicit mappings" (the literal leniency
   reading) would pass every suite. Add one table row to `TestJSONProfile`.

## What I decided NOT to propose, and why

- **Invalid UTF-8: JSON silently U+FFFD-substitutes where BSON rejects.** Encoding/
  json sanitizes invalid UTF-8 before `checkString` ever sees the bytes, so the JSON
  profile can never produce the ReasonTypeMismatch that `checkString` documents
  (value_test.go:152-163 covers the BSON-side only). The stored value is valid UTF-8
  either way and the sanitising is upstream-consistent Go behaviour; tightening it
  to a rejection is a profile-strictness product call. Sketched in the review for
  the next run, not queued.
- **DetectFormat treats a UTF-8 BOM as FormatInvalid.** encoding/json also refuses a
  BOM, so the two layers agree; a BOM'd payload is rejected with the right reason.
  Not worth a line.
- **`t` below-before-window / BSON `t` out-of-window**: same `dateTimeFromMillis`
  code path already pinned by the datetime-value rows. The duplicate-BSON-key
  rejection, custom MaximumSize, string-cap-above-payload-cap, and 1024-element cap
  for both formats are all asserted.
- **Performance**: the encode path is allocation-free-by-design (byte-slice writer),
  decode uses the raw-document API; arrays allocate once via `Values()`, bounded by
  the 64 KiB gate. No workload-specific hotspot — nothing to measure.
- **New features**, none surfaced from reading; nothing for `.mule/for-giulio.md`.
