## What I found

### 1. The whole Realm Management error-mapping is asserted only by integration-tagged tests (category 2)

`writeInterfaceError` (http.go:352-399), `writeError` (http.go:402-425),
`writeViolations`/`renderViolationsBody` (http.go:434-533) and `validationDetail`
(http.go:562-568) encode the exact 403/404/409/422 statuses and bodies the
interface, trigger, policy and config surfaces put on the wire. Their only
coverage is `http_test.go` and `dashboard_compat_test.go`, both
`//go:build integration` (TimescaleDB). The non-integration files never
reference them (rg over `*_test.go`), so on the Pi — where integration suites
cannot run — a regression that, say, moved `ErrNameCollision` off 409, dropped
the `errMajorNotFound` → 404 mapping, or reordered the `errors.As(err, &ve)`
case below `ErrValidation` would pass the entire gate unnoticed. The
distinguishing trigger of the 1.2 taxonomy (`writeInterfaceError`'s 403 for
`ErrInterfaceMajorNotZero`/`ErrInterfaceInUse` vs `writeError`'s 422 for the
same sentinels) is exactly the kind of thing that silently rots.

All of these are callable without a DB: `writeInterfaceError`/`writeError` never
touch `a.svc`, and `renderViolationsBody`/`validationDetail`/`majorParam` are
pure. `ViolationsError` is constructible from outside the package via its
exported `Violations`/`MappingCount` fields, so the nested changeset envelope
(interface-level fields + the full-length aligned `mappings` array, `{}` for
clean entries) can be pinned byte-for-byte.

### 2. `writeDetailedMapping`'s properties branch has no container-free test (category 2)

`detailed_required_encrypted_test.go` pins the **datastream** branch of
`writeDetailedMapping` (detailed.go:65-75) exactly, but the properties branch
(detailed.go:61-63: `endpoint`, `type`, `allow_unset`, and nothing else) is only
reached through integration `detailed_test.go`. A regression that emitted a
datastream-only field on properties mappings, or dropped `allow_unset`, passes
the Pi gate. Small, but it is an existing contract with a one-line test.

## What I decided NOT to propose, and why

- **`writeError`'s `store.ErrInterfaceMajorNotZero` (422) and
  `store.ErrInterfaceInUse` (422) branches (http.go:414-419) are unreachable.**
  Only the six interface handlers route to `writeInterfaceError` (comment
  http.go:349-351), and none of `writeError`'s callers (triggers, policies,
  config, `deleteDevice`) invokes an interface store op. So the two branches are
  dead. Deleting them is a one-file clarity edit, but `docs-sync-rm-delete-interface-status`
  (done) deliberately tied the RM spec's delete-interface examples to the
  `writeInterfaceError` 403 form *and named these exact `writeError` strings* as
  the wrong source; removing them now is churn with no safety gain, and they
  cost nothing as defense if a future non-interface path reuses the sentinel.
  Recorded so the next pass does not re-derive it.
- **`SetAuthKey` stores a single-element key slice (service.go:636).** The
  "rotation window joins all keys" comment (service.go:627) reads as if several
  keys were stored, but every writer (create store/realms.go:54-61, PATCH
  store/realms.go:165, this) stores one; already escalated in `.mule/for-giulio.md`
  (lines 660-666) as a non-bug. Not re-raising.
- **`DeleteDevice` disconnects before the existence check (service.go:122-124),
  and `OnDeletionStart` fires after the kick (service.go:126-128).** For a
  well-formed-but-unknown ID the disconnect is a no-op, and upstream's ordering
  of delete vs disconnect is not something I can verify from here; flagged, not
  proposed.
- **`ListPolicies` does not sort (service.go:540-555) while `ListInterfaces` and
  `ListTriggers` do.** Not a bug: `store.ListTriggerPolicies` is `ORDER BY name`
  (store/policies.go:69). Left alone.
- **`listInterfaces?detailed=true` and the names-only path share no helper.**
  Intentional per issue #66; not a refactor worth a tick.
- **`validationDetail`'s manual prefix slice (http.go:562-568).** Same non-issue
  the 09-09 review recorded; the new test task above pins its exact behaviour
  rather than rewriting it.
- **New features / DESIGN conflicts.** None found: the package tracks
  DESIGN §3.7 and the recorded deviations (§60 retention null→0, sync delete).

## Verdict

The package is unchanged since the 09-09 pass and remains defensively coded;
