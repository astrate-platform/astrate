# Review — internal/engine/forward (2026-09-26)

First review of this area, so no prior file to extend. Chosen because it is the only
`internal/engine` sub-package with no review behind it, and because it is the seam where
a tenant's event payload leaves the process for something the mule does not control.

Three claims below were measured with a throwaway `net/http` program in `/tmp` rather than reasoned
about, because all three are about what the standard library does with Astrate's inputs.

## What I found

**1. `New` validates the URL and the method at boot but not the static header names — so a typo in
`triggers.forward.static_headers` breaks every delivery instead of the boot.** The comment at
http.go:42-45 states the rule this package holds itself to: "an unusable endpoint must fail here
rather than surface once per delivery". `cfg.StaticHeaders` goes straight into the struct
(http.go:68) and is applied per delivery with `req.Header.Set` (http.go:110-112), and `net/http`
validates header names and values only at write time. Measured:

| static header | result |
| --- | --- |
| `X Bad Name: v` | `forward: Post "…": net/http: invalid header field name "X Bad Name"` |
| `X:Foo: v` | `net/http: invalid header field name "X:Foo"` |
| `X-Foo: "a\nb"` | `net/http: invalid header field value for "X-Foo"` |
| `X-Foo: "a b"` | fine (spaces are legal in a value) |

So a single misconfigured header name makes the process boot clean, accept triggers, count
`astrate_engine_trigger_deliveries_total{outcome="failed"}` on every custom action, and log
"custom trigger action failed" (actions.go:499) forever. The fix is nearly free: the RFC 7230
field-name grammar *is* the token grammar `validMethod` (http.go:77-95) already implements, plus a
CR/LF check per value.

**2. The static-headers-win rule is documented and completely unasserted.** http.go:22 says
static headers are "applied after the fixed ones", and the loop at 110-112 does run after the three
`Set`s at 107-109 — so a static `astarte-realm: spoofed` overwrites the realm-routing header.
Measured: the bus sees `Astarte-Realm="spoofed"`. `TestStaticHeaders` (http_test.go:86-118) asserts
only the *non-colliding* case, so reordering that loop above the fixed headers, or filtering
reserved names, would leave the suite green. Whether override-shall-win is the right answer is a
call (see the escalation), but whatever it is should be pinned by a test rather than by a comment.

**3. A non-2xx forward reports the status code and nothing else, after discarding the body
unbounded.** http.go:117-120 copies the entire response body into `io.Discard` with no limit, then
http.go:121-123 returns `forward: status %d`. The one thing an operator needs to debug a 500 from
the bus is gone. The sibling webhook request in the same codebase does bound its drain —
`io.LimitReader(resp.Body, 1<<20)` (actions.go:626) — so the two near-identical request paths have
drifted apart on exactly the line that matters here.

**4. `marshalEnvelope` has no direct test, and the wire shape is only checked through a re-parse.**
`rg marshalEnvelope` finds two callers and no test. envelope.go:6-8 makes a strong claim — "every
Forwarder implementation in this package must produce byte-identical envelopes" — but both test
files unmarshal the body into `bodyShape` (http_test.go:24-29), which cannot see key order or the
exact bytes, and which would pass just as happily if a field were renamed on both sides. The
nil-vs-empty normalisation rule *is* pinned (TestEmptyNonNilActionAndEvent, http_test.go:212, with
a comment explaining that it is the row that binds), so the gap is narrower than it first looks: it
is the exact-bytes claim that is unasserted.

**5. The NATS forwarder reports success for a publish that has only been buffered, and its async
errors bypass Astrate's logger entirely.** `nats.Conn.Publish` (nats.go:4229) calls
`publish` (4424), which appends to the client's buffered writer and returns; the socket write
happens later on the flusher goroutine. A later failure goes to `Opts.AsyncErrorCB`, and because
`NewNATS` passes no options (nats.go:36) that is nats.go's own `defaultErrHandler` printing to
stderr (nats.go:1853-1856) — no `*slog.Logger`, no realm, no trigger name — while
`Executor.forward` has already counted the delivery `forwarded` (actions.go:503). `Forward` also
takes `_ context.Context` (nats.go:44), so the 10s `RequestTimeout` the executor sets at
actions.go:487 is not honoured on this path. Not queued: the fix needs a logger plumbed through
`NATSConfig` → `newnats_nats.go` → `main.go:273` (three files, one of them an interface-adjacent
signature), and the only test I can imagine induces a write failure by killing the container
mid-publish, which is racy — a task whose test cannot be made to fail reliably is a wasted run.
Escalated instead.

## Suggested tasks (appended to todo.md)

- `forward-static-header-validation` — reject at boot what `net/http` will refuse at delivery
- `forward-static-headers-override-test` — pin the documented apply-after-the-fixed-headers rule
- `forward-status-error-body` — bound the drain, surface a prefix of the bus's error body
- `forward-envelope-bytes-test` — pin the envelope's exact bytes, not just its re-parsed fields

## Decided NOT to propose, and why

- **Unbounded response drain as a DoS.** Real, but only in combination with a hang, and the hang is
  already bounded: the executor wraps every forward in `RequestTimeout` (actions.go:487, default
  10s, actions.go:195). Folded into `forward-status-error-body` as the `LimitReader` half rather
  than proposed as its own task — io.Discard does not grow memory, so there is no allocation
  argument, only a wasted-IO one.
- **`http.DefaultClient` following redirects and re-sending the realm header and body to another
  host.** Measured (307 preserves method and body): the second server saw
  `Astarte-Realm="leaky-realm"`. Not queued: the endpoint is operator-configured, so the redirect
  target is operator-controlled too, and the webhook client behaves identically
  (actions.go:621) — a forwarder-only fix would make the two paths inconsistent. Escalated as a
  question about `CheckRedirect` for both.
- **Blocking the upstream header blocklist for bus forwarder headers.** The action path enforces
  it (validation.go:140-155); `triggers.forward.static_headers` gets no such check. Measured that
  net/http ignores a static `Host` and derives `Content-Length` from the body anyway, so the
  practical harm is "silently ignored", not "corrupting" — and *which* names to block is a policy
  call. Escalated.
- **Never closing or flushing the NATS connection at shutdown.** `main.go:116` builds it and
  `shutdown` (main.go:482-502) has no forwarder teardown, so the pending buffer is dropped on
  exit. The fix is a lifecycle method on `triggers.Forwarder` — a three-file change to an
  interface, i.e. a design decision. Escalated.
- **A `go test -bench` task for the forward hot path.** No workload to name: forward volume is
  driven by how many custom-action triggers an operator installs, which is a configuration, not a
  code property. The one allocation worth noting (`bytes.NewReader` + `json.Marshal` per delivery,
  http.go:99-103) is already two allocations against a network round trip.
- **Whitespace-only `action`/`event` making `marshalEnvelope` fail.** Reachable only through a
  mustache template that renders to nothing but spaces (actions.go:426-433), and the failure is a
  clean `forward: marshal:` error rather than a corrupt envelope. Not worth a task.
